# traps 写作规范

本文件是踩坑记录的唯一准入标准与体例约定。写 traps 前必须照此执行。

## 准入三问（任一不过则不得写入）

### ① 可迁移性——换个完全不同的业务、不同的会话，还成立吗？

不成立（只有"再次改同一文件"才有用）→ **禁止入 traps**。

例：只有一帧特效没播出来 → 一次性现场，拒绝。

### ② 名称硬否决——条目含具体业务名吗？

含业务组件类名、配置字段名、协议名、表名、常量值 → **剥离名称改写成规律再评估**。

区分标准：
- **API 名可保留**（`GetChild`、`AddItemFromPool`——框架 API 会一直存在）
- **业务名必须剔除**（`StatisticsListItem`、英雄/怪物/装备名——会改名、会下线）

### ③ 正确性——断言与当前代码一致吗？

相左、已过时（代码已重构/改名）、无法核实（传闻/纯推测）→ **不得写入**。

写之前先看真实代码或真实输出。

## 体例

1. **索引前先 grep**：确认无同义条目；有则合并或引用权威表述。
2. **单条只讲一个规律**，标题陈述规律本身（不写组件名/业务名）。
3. **正文固定句式**：`违反：后果；必须：做法`。固定句式让 AI 扫读时不需要解析自然语言。
4. **禁止图形符号**（箭头、对勾、叉号），用语义化自然语言。

示例：

```
### 事件订阅必须成对退订
违反：只在 OnOpen 订阅、OnClose 不退订，重连或重进界面时会重复执行事务。
必须：订阅与退订写在同一生命周期对的相邻位置，退订检查 null。
```

## 三类知识的边界（不得混淆）

| 载体 | 内容 | 强制力 |
|---|---|---|
| `rules/` | 稳定的工程约定 | 强制 |
| `traps-*.md` | 带反例的易错点，rules 的实操补充 | 强建议 |
| `feature-map/` | 功能 → 文件索引 | 参考 |

**三者对同一问题必须口径一致**——发现矛盾就地统一，禁止出现第三种说法。

演进方向单向：成熟的工程规律由维护者从 traps 提取进 rules；提取后从 traps 删除。

## 5000 token 清理阈值

任一 `traps-*.md` 超过 5000 token 即触发清理，处置顺序：

1. 合并相似条目
2. 删除已被 rules 覆盖的条目
3. 通用规律迁移到 `rules/`

## 禁止写入

- 会话上下文（"本次任务中……"）
- 待办状态（"待提交""待验证"）——那是任务管理，不是工程规律
- 已被用户裁决否决的方案（除非同时记录裁决理由，防止未来重提）
