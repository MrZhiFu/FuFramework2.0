# 框架层踩坑

规范见 `rules/framework/`、`rules/architecture/`。本文件记 rules 未覆盖的实操反例。

### 委托类型并存必须双字典 + 合并分发
违反：用包装闭包把旧/新两种 handler 适配到同一字典，退订时找不到原委托，订阅泄漏。
必须：两套委托类型各存一个字典，派发时合并遍历；确需包装时必须验证包装实例的相等性成立（闭包包装不成立）。

### Editor 面板反射热更类型有三层炸点
违反：改热更侧类型名/签名后只改业务代码，Editor 面板静默失效或空引用。
必须：同步三处——① 泛型约束（基类变了要改适配器约束）；② 反射字段名（改名必须同步 `GetField` 字符串，并加 `?.` 判空降级）；③ 域重载窗口期 NRE（自愈靠 ResetReflection 重绑）。

### 探针的标记与汇总行用词必须互斥
违反：结果文件里汇总行包含待统计的子串，用全文计数会虚加。
必须：探针标记名与汇总行用词互斥；或按行首匹配统计。

### 批量常量收敛先划定不碰区
违反：把整个框架的常量无差别收敛，改动波及核心与游戏层，引入无谓风险。
必须：先明确"不碰"的模块（核心与游戏层业务），只收敛框架模块。

### 为零调用方预留的优化会被裁定为过度设计
违反：为"将来可能的高频调用"预先堆缓存机制，实际零调用方。
必须：优化前先查真实调用方；可读性优先，机制等真实热点出现再加。

### 文档里的实现描述会漂移，以代码为准
违反：照着模块 README 或架构文档写规则，文档里的结构可能早已重构。
必须：写规则/改代码前用 grep/ls 核对真实符号；发现文档与代码不一致时以代码为准，并把漂移记录在案。

### 外部工具的能力清单也必须实测，不能凭印象
违反：套用别的项目/过往会话里的工具名，本项目根本没有该工具，写出的指令无法执行。
必须：写任何工具名、命令、参数前，先跑一次该工具的清单/schema 命令确认（如 `Tools/UnityCli/unity-cli.exe tool list`、`Tools/UnityCli/unity-cli.exe tool schema <名字>`）。同一个技能里出现"没有 X"和"用 X"两种说法，就是漏核实的信号。

### 断言"没有某能力"前要查全量清单，不能只 grep 关键词
违反：grep 几个关键词就断言"工具不存在"，漏掉了真正可用的替代能力（如性能分析、UI 自动化工具），写出的方案比实际可行的差一大截。
必须：断言"没有 X"前看**全量清单**（`tool list` 完整输出、桥接包路由表 `BridgeCommandRouter.cs`）；再确认一次"有没有等价能力"，而不是只回答"有没有这一个名字"。
