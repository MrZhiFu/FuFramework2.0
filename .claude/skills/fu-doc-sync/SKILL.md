# 提交前文档同步

代码改完不等于做完。四类知识可能都需要跟着动。

## 1. feature-map（功能结构变了才动）

触发条件：

- 新增/删除/移动了模块或关键目录
- 某个功能的主要文件路径变了
- 新增了重要入口（如新的菜单、新的生成脚本）

动作：更新 `.claude/memory/feature-map/<域>.md` 的「功能 → 路径」行。

**只做索引**——不写实现细节与业务结论。

## 2. traps（踩了新坑才动）

先过 `memory/traps-authoring.md` 的**准入三问**：

1. 可迁移性——换个业务/会话还成立吗？
2. 名称硬否决——含业务组件名/字段名吗？（API 名可留，业务名必剥）
3. 正确性——与当前代码一致吗？

通过 → 写进对应 `traps-<域>.md`，用「违反：…；必须：…」句式。
不通过 → **不写**。

同时更新 `memory/MEMORY.md` 的索引行。

## 3. rules（规则与现实不符才动）

触发条件：

- 改动使某条规则的描述失效
- 发现规则里有错误事实（路径、类名、命令、版本）

动作：直接改 `rules/` 对应文件。**改之前先 grep 核对真实符号**——不要凭记忆或文档写。

## 4. 架构文档漂移

`Docs/项目架构与技术栈.md` 与代码不一致时：

- 本次改动造成的漂移 → 就地修正
- 与本次无关的既有漂移 → **报告给用户**，不擅自大改

## 检查清单

- [ ] 功能结构变了吗 → feature-map 更新了吗
- [ ] 踩新坑了吗 → 过准入三问了吗
- [ ] 规则里有失效事实吗 → 改了吗
- [ ] `MEMORY.md` 索引与实际文件一致吗
