# FuFramework 重型全流程

约 13 个 Phase。**主 Agent 只做编排、评审、把关。**

## 开场场景判定

| 场景 | 识别 | 执行范围 |
|---|---|---|
| 全新功能 | 从零开始，需要界面设计与需求文档 | Phase 1-13 全跑 |
| 中等任务 | 改/扩已有功能，2+ 文件 | 跳过 Phase 5，其余全跑 |
| 实现任务 | 用户明说界面已做好 | 跳过 Phase 5 与 UI 搭建，简化 Phase 7 |
| 琐碎改动 | 1 文件、1-2 行 | 改用 `fu-quick-dev` |
| 中等任务 | 改/扩已有功能、2-8 文件、无需完整文档流 | 优先改用 `fu-standard-dev` |

## 四条核心约束（地基）

1. **主 Agent 不写代码、不探索代码。** 协调、派发、评审；所有实现与代码库探索交给子代理。主 Agent 永远不直接对源码用 `Read/Grep/Glob`。
2. **显式批准关卡。** 没有用户明确批准，禁止进入下一阶段。批准 = 用户自己语言里的清晰肯定（"同意""OK""开始""approved"）；**沉默、追问、观察（"看起来没问题"）、犹豫（"嗯……好吧"）都不算批准**。
3. **不许跳阶段。** 每个阶段都有存在理由；可以**简化**（内容更短），不能**跳过**。哪怕再简单，设计也至少要有：影响文件清单 + 选定方案 + 成功标准。
4. **先证据后结论。** 先跑验证、读输出，再宣布结果。

带预设选项的问题用 `AskUserQuestion` 弹选择框，不要纯文本罗列。

## Phase 1: 探索与发现

按维度**并行**派 `Explore` 子代理（同一条消息里一起派，2-4 个）：

- 架构与数据流（**必选**）
- 模块层（碰业务逻辑/数据时）
- UI 层（碰面板时）
- 配置与协议（碰表/网络时）

派发时给每个子代理：**域、要找什么、`feature-map/_index.md` 的路径、`traps-<域>.md` 的路径**。

汇总成统一理解，直接进入下一阶段（不需用户确认）。

## Phase 2: 范围检查

- 涉及多子系统或 > 10 文件 → 建议拆分，向用户确认范围。
- 拆分后本流程只负责其中一块。

## Phase 3: 需求澄清

- **一次一个问题**，覆盖 11 个维度：数据流 / 模块边界 / 算法 / 代码结构 / 资源 / UI 布局 / 字段 / 控制器 / 关系 / 配置表 / 协议。
- 每个问题必须带**真实案例**。
- **停止条件**：能一句话描述任务、列全文件、说清成功标准。

## Phase 4: 流程分析与确认

用箭头链写三条流：

- 玩家操作流
- 端到端数据流
- UI 交互流

**必须等用户明确确认。**

## Phase 5: 文档准备（仅全新功能）

需求文档 + UI 规格（`uispec.md`，放 `.claude/plans/`）。文档确认后进入下一阶段。

## Phase 6: 设计与批准

- 提 2-3 个方案与取舍。
- 固定骨架呈现：**做什么 / 例子 / 规模 / 需要你决定的 K 项**。
- 设计文档存 `.claude/plans/YYYY-MM-DD-<功能>-design.md`。
- **用户明确批准**才能继续。

## Phase 7: 实施计划

写**自包含**的任务计划（`.claude/plans/YYYY-MM-DD-<功能>-plan.md`）。

硬规则：

- 每个任务 **≤3 个文件**。
- 每个任务内联**真实代码块与验证命令**——子代理只拿到任务文本，**不会去读设计文档、uispec 或需求文档**。
- UI 任务内联组件名、控制器、状态、元素布局。
- 架构任务内联约束与决策。
- 协议/配置任务内联字段定义与表设计。
- 每个任务写 `Interfaces: Consumes / Produces`（精确到签名）。
- 写计划前读本域 `traps-*.md`。

**用户批准计划** + 用 `AskUserQuestion` 选执行模式（主 Agent 自己实现 / 派子代理）。

## Phase 8: 计划预检

整体扫一遍计划的内部矛盾与"计划自己规定的缺陷"。一次性批量报告，不边跑边打断。

## Phase 9: 执行

逐任务：

```
1. 基线快照：git stash create 或在临时目录记下改动前状态
2. 给实现子代理一份自包含任务简报（文件路径 + 代码块 + 验证方式 + traps 条目）
3. 子代理实现并写报告（改了什么、怎么验证的）——不 commit
4. 生成该任务的 diff 供评审
```

**不要相信子代理的口头 DONE**——Phase 11 独立审 diff。

## Phase 10: 编译验证与修复循环

```bash
bash .claude/verify-compile.sh
```

0 错误才进入下一阶段。有错派修复子代理，主 Agent 不自己修。

## Phase 11: 三阶段评审（顺序不可逆）

| 阶段 | 审什么 | 方式 |
|---|---|---|
| 1. Spec 合规 | 实现的是不是要求的东西，不多不少 | 独立读 diff，逐行对任务书 |
| 2. 代码质量 | 五条铁律 / 三项机械检查 / 风格 / traps | 按 `fu-standard-dev` 的 2.5 清单 |
| 3. 全分支终审 | 跨任务的集成问题 | 读全分支 diff |

每阶段通过才进下一阶段。

**修复轮恢复同一个实现者**（保留其上下文），不新派。

## Phase 12: 用户验收（不可跳）

按质量报告模板汇报 + 给游戏内验证步骤（玩家视角）。

**必须等用户明确回复验收通过。**

## Phase 13: 收尾

1. 文档同步（`feature-map`、`traps`、`rules`）
2. 流程复盘（用户确认后更新技能）
3. **列清单问用户确认后**单次提交（`[AI]<type>: <中文描述>`）

## 可证伪的验证

实现者的自检必须是**可证伪**的：

- 每个探针要**点名它能抓住哪个 bug**。
- 期望值**独立推导**（从配置原始值/手算值来，不能抄运行时现值）。
- 做**变异检查**（把代码改坏，探针必须失败）。
- 修复场景走**红绿**：修复前捕获异常值（红），修复后同一探针恢复期望值（绿）。

"探针通过"本身不证明任何事——一个从不失败的探针等于没测。

## 常见误区

| 误区 | 纠正 |
|---|---|
| "这个任务简单，不用走流程" | 简单任务正是未检查假设最浪费时间的场景。设计可以短，但必须存在。 |
| "用户说直接开始" | "开始"≠ 批准设计。必须先呈现方案并拿到明确批准。 |
| "我自己读一下代码就行" | 主 Agent 永远不读源码；探索交给并行子代理。 |
| "我熟悉这个系统，可以跳过探索" | 熟悉提高设计质量，不是跳过流程的理由。 |
| "编译错误我自己顺手修了" | 主 Agent 不写代码；派修复子代理。 |
| "子代理说 DONE 了，不用审" | 不要信报告；独立读 diff。 |
| "修复太慢，每轮新派一个实现者" | 恢复**同一个**实现者。 |
| "用户沉默 = 同意" | 沉默、追问、观察、犹豫都不算批准。 |
| "探针过了，逻辑就验证了" | 不点名失败模式的探针抓不住任何东西。 |
