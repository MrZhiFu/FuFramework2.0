# FuFramework 轻量开发流

小需求 / 小 Bug 的最短安全路径。不写设计文档、不派子代理、不提交、不同步文档。

## 适用判定

**全部满足**才用本技能，否则走 `fu-standard-dev`：

- 改动 ≤ 3 个文件
- 单技术层（纯 UI / 纯模块 / 纯配置表 / 纯逻辑）
- 逻辑明确，无需设计取舍
- 不新建系统 / 类骨架

边界模糊时，宁可走稍重的 `fu-standard-dev`。

## 沟通规则：具体重放，不用符号链

报告根因、边界处理、最终结果时，写成"玩家做某操作 → 系统处于某状态 → 出现某结果"的具体重放。

- ❌ "回调链断了，状态没清，语义更顺" —— 裸判断，用户无法想象。
- ✅ "关闭面板时若动画还在播，先等它播完再真正关闭。重放：玩家打开面板 → 关闭动画播完前又点了一次关闭 → 动画播完后面板干净消失，不闪烁。"

## 流程

```
理解确认 → 定位 → 方案确认 → 实现 → 编译验证 → 自查 → 报告
```

### 1. 理解确认

一句话复述要做什么（改什么 / 期望结果），让用户确认。

只在**确实有歧义**时提问，最多 1-2 个，优先给选择题。无歧义直接下一步。

### 2. 定位

只读完成任务必须的最少代码。

- **禁止全量扫描**。
- 知道改哪 → 直接读目标文件。
- 不确定 → 读 `.claude/memory/feature-map/_index.md` 定位域 → 读域文件拿路径 → 精读。
- **修 Bug 必须先定位根因**：优先看 `git diff` / `git log` 里相关文件的近期改动，**新引入的代码与数据优先怀疑**。用一句话报告"错在哪、为什么错"。

#### 定位纪律：抓最强线索，走最短链路

Bug 现象里通常藏着一根**最强线索**——某个触发动作（选中/点击/打开 X）或某个差异化表现（相同配置只有部分对象异常）。抓住它，沿"触发动作 → 它对异常对象做了什么"走，**不要绕到 shader / 渲染管线 / 相机 / 池化等间接因素**。

四条铁律：

1. 有明确触发动作 → 第一步精读该动作的处理代码。
2. "相同配置、部分对象表现不同" = 有代码做了差异化设置 → 去属性/数据层找，不是渲染管线问题。
3. 锁定**唯一写入入口**：异常属性通常只有一两个写入点，grep 该属性的写入函数 → 向上追调用链。
4. 静态最短链路没走通前不发散，别急着加日志或升级流程。

**自检**：你正在查 shader / 渲染管线 / 相机，但现象里有"选中/点击/打开"触发词？停下，回到那个动作的处理代码。

#### 运行时查证（可选）

用 `Tools/UnityCli/unity-cli.exe tool call eval_csharp --json '{"code":"<C# 表达式>"}'` 直接求值取证——不停止游戏、不改代码、不重编译。查不出来再写 `[MenuItem]` 探针（见 `fu-unity-cli-usage` 技能与 `rules/tooling/runtime-profiling.md`）：

- **确证型**：静态链路已锁定嫌疑点，但代码无法确证（怀疑缓存是旧值、推送时序错位）→ 取证。
- **定位型**：纯数值/状态异常且无线索 → 先逐层探数据链（显示值 → 缓存值 → 配置原始值）定位出错层，再精读。

定位型仅限"无线索 + 纯数值异常"；有触发线索必须静态优先。

### 3. 方案确认

极简：一句话说清怎么改，必要时给 2 个选项让用户选。**用户没反对即执行**。

### 4. 实现

- 遵守 `.claude/rules/coding/coding-standards.md` 与五条铁律。
- 动手前读 `.claude/memory/traps-*.md` 对应域，确认不踩已知坑。

### 5. 编译验证

```bash
bash .claude/verify-compile.sh
```

0 错误才算通过。有错先修，不进入下一步。

### 6. 自查

- 五条铁律有没有违反（Task / Coroutine / LINQ / 反射 / 取消链所有权）
- 命名规范（`m_` / `Async` 后缀 / `E` 前缀）
- 注释是否为中文 XML 文档注释
- 改动是否超出必要范围

### 7. 报告

- 结论 + 证据（改了什么、验证结果）
- 一句话重放（玩家视角看到的变化）
- **不提交**——等用户确认后再按 `git-conventions` 统一处理
