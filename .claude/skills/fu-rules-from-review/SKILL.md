# 从发现到知识

评审、排查、重构里发现的规律，要么沉淀，要么忘记。沉淀时先判断进哪一层。

## 第一步：这是哪一类

| 特征 | 去向 |
|---|---|
| 稳定的工程约定，AI 每次都该遵守 | `rules/` |
| 带反例的易错点，需要"现象 → 查什么" | `memory/traps-*.md` |
| 功能/文件位置 | `memory/feature-map/` |
| 用户对协作方式的偏好 | 用户记忆（不进仓库） |

**判断标准**：换个业务还成立、且是"必须怎么做" → rules；换个业务还成立、但是"曾经怎么错、症状是什么" → traps。

## 第二步：准入三问（对 traps）

1. **可迁移性**——换个完全不同的业务/会话还成立吗？
2. **名称硬否决**——含具体业务组件名/配置字段/协议名吗？（API 名可留，业务名必剥，改写成规律）
3. **正确性**——与当前代码一致吗？相左、过时、传闻 → 不得写入。

**写之前先 grep 真实符号**。凭记忆写的类名/路径极可能已经不存在——这是最容易犯的错。

## 第三步：查重

- 先 grep 现有 traps 与 rules 的相关关键词。
- 已有同义条目 → **合并或引用**，不重复立条。
- 已被 rules 覆盖 → 不写进 traps（单一事实源）。

## 第四步：写成什么形态

**rules**：`必须/禁止/不得` 句式，表格优先，给路径与本文件的分工说明。

**traps**：二选一——

- 规律型：`### 标题\n违反：后果；必须：做法。`
- 诊断型：加入对应域的「症状 → 先查什么」表格

禁止图形符号；一条只讲一个规律。

## 第五步：登记

- traps → 更新 `MEMORY.md` 索引行
- rules → 检查 frontmatter `paths:` 是否覆盖新内容所在目录（内容在 A 目录、paths 只含 B 目录 → 规则永远不加载）
- 演化方向单向：成熟的 traps 规律应被提取进 rules，提取后从 traps 删除

## 反模式

| 反模式 | 后果 |
|---|---|
| 把一次性现场写成 traps | 三个月后失效且没人敢删 |
| 同一事实在 rules 和 traps 各写一份 | 改一处漏一处，出现第三种说法 |
| 凭记忆写类名/路径 | 写出不存在的符号，AI 照抄即错 |
| 只写"要注意 X"不给做法 | 无法执行 |
