# FuFramework 中等任务开发流

```
需求澄清 → 方案确认 → 复杂度评估 → 实现 → 编译验证 → 代码评审 → 用户验收 → 提交 → 文档同步
```

**主 Agent 可以自己实现**（不像 `fu-full-dev` 强制派发子代理），但跨层任务要派专家子代理。

---

## Phase 1: 需求澄清

### 1.1 读取上下文（强制，三步定位）

1. **域定位**：读 `.claude/memory/feature-map/_index.md`，按需求决定加载哪个域文件。
2. **知识与规则**：按域读 feature-map → `traps-<域>.md` → 对应 `rules/` 文件。
3. **源码**：读前两步得到的**定向路径**。**禁止盲搜全仓。**

### 1.2 需求提问

- **一次只问一个问题**，直到没有歧义、遗漏或疑点。
- **具体案例优先**（强制）：任何面向用户的消息——问题、解释、方案、风险汇报——都必须先给**具体场景案例**（真实的界面、配置行、玩家操作），抽象只做辅助。
  - ❌ "仅 UI 层 | 修改现有面板" —— 抽象标签，用户想象不出。
  - ✅ "仅 UI 层 | 例：在背包面板加一行容量提示；在主界面加离线收益图标"
- 问题形式按复杂度选：图示式预览 → 普通多选 → 开放式。

### 1.3 方案确认（强制）

原则：**结论先行（BLUF）+ 决策驱动 + 具体案例**。用户在这个关卡只做两件事：批准方案、解决开放决策。

默认输出格式：

```
## <功能> — 方案
做什么: <一句话：目标 + 怎么做；复用什么、新增什么>
  例子: <玩家在真实场景里看到/做到什么；真实值/形状/行为>
规模: 约 N 个文件 / M 层（列出层）

需要你决定的 K 项（逐个弹窗）
→ 回复 "detail" 看完整调用链/签名/风险；回复 "start" 按推荐执行。
```

随后用 `AskUserQuestion` 逐个呈现开放决策。**没有开放决策就明说，跳过弹窗。**

**实现细节是点播制**：用户回 `detail` 才展开。默认不给。

**批准门槛**：等用户明确回 `start` / `OK` / "开始"。**沉默、追问细节、补充背景都不算批准。**

## Phase 2: 实现

### 2.0 复杂度评估（四维判定，强制）

| 维度 | Simple | Complex |
|---|---|---|
| 文件数 | ≤ 8 | ≥ 9 |
| 业务模块耦合 | ≤ 2 个域 | 3+ 个域 |
| 跨技术层 | ≤ 2 层 | 3+ 层（如 UI+配置+模块+网络） |
| 改动规模 | 补逻辑/加字段/改文本/加方法 | 新类/系统骨架/独立服务 |

**四维全 Simple → 主 Agent 直接实现；任一维 Complex → 派子代理。**

额外触发 Complex：存在多个可并行的独立子任务。

### 2.1 前置（按需）

| 场景 | 动作 |
|---|---|
| 加 UI 文本 | 查本地化表 → 加 key（代码引用则 `is_code=true`）→ 重跑生成 |
| FairyGUI 组件改动 | 走 `fu-fgui-edit` 技能 |
| 配置表改动 | 走 `fu-config-edit` 技能 |
| 协议改动 | 走 `rules/framework/network-protocol.md` 的导出流程 |

### 2.2 Simple 模式：主 Agent 直接实现

按 `rules/coding/coding-standards.md` 写。**每改一个文件先读对应 traps 域**。

### 2.3 Complex 模式：文档 + 子代理

核心原则 **transfer, don't re-discover（传递，不重新发现）**：

- Phase 1 已付的探索成本（域知识、需求结论、代码事实）必须**显式交给子代理**。
- 子代理的职责是**验证**已知事实并实现，**不是**从 feature-map 重新推导。
- 给子代理的简报必须自包含：目标、涉及文件、已有结论、接口契约、验证方式。

### 2.4 编译验证

```bash
bash .claude/fu-unity-compile.sh
```

0 错误才继续。有错走修复循环，不要边修边加新功能。

### 2.5 代码评审

自查清单：

- **五条铁律**：无 `Task` / 无协程 / 无 LINQ / 无运行时反射 / 异步链有所有者
- **三项机械检查**：`m_` 前缀、`Async` 后缀、`E` 前缀
- **风格**：Tab 缩进、K&R 括号、中文 XML 注释、无魔法数字
- **traps 复核**：本域 traps 逐条对照
- **范围**：有没有顺手改了无关代码

发现 Critical/Important → 修；Minor → 记录后放行。

## Phase 3: 用户验收

按三段式汇报（意图 / 现状 / 案例）：

- 改了什么文件（列清单）
- 验证结果（编译输出、实测证据）
- 游戏内验证步骤（玩家视角：打开哪个界面、点什么、预期看到什么）

**必须等用户明确回复验收通过。**

---

## Phase 4: 提交

**提交前必须列清单询问用户确认**（见 `rules/coding/git-conventions.md`）：

```bash
git status --short   # 先看清楚有什么
```

- 只提交本次任务的改动
- 非本次会话产生的改动绝不纳入
- 提交信息 `[AI]<type>: <中文描述>`

---

## Phase 5: 文档同步

- 改动影响了功能结构 → 更新 `feature-map/` 对应域
- 踩到新坑 → 按 `traps-authoring.md` 准入三问决定是否入库
- 规则与现实不符 → 更新 `rules/`

---

## 技能边界

| 不适用场景 | 该走什么 |
|---|---|
| ≤ 3 文件的小改动 | `fu-quick-dev` |
| 全新系统 / 大型重构 | `fu-full-dev` |
| 纯配置表 | `fu-config-edit` |
| 纯 FairyGUI 编辑 | `fu-fgui-edit` |
