只要你觉得某个技能有 1% 的可能适用于当前工作，就**必须**先调用它。

如果技能适用，你没有选择权。必须使用。

这不可协商、不可省略，不能靠自我说服绕过去。
</EXTREMELY-IMPORTANT>

## 指令优先级

项目技能可以覆盖系统默认行为，但**用户指令永远优先**：

1. **用户显式指令**（CLAUDE.md、rules、直接要求）——最高
2. **项目技能**（`fu-*` 等）——与系统默认冲突时覆盖系统默认
3. **默认系统提示**——最低

CLAUDE.md 或 rules 说"不要做 X"而技能说"总是做 X"时，听用户的。

**本项目流程一律走 `fu-*` 技能族**，不调用插件级的通用流程技能。

## 规则

**在做任何回应或动作之前，先调用可能相关的技能**——包括澄清提问和探索代码之前。

流程本身也算任务：写计划前先查 `fu-standard-dev`，改代码前先查 `fu-quick-dev`。

调用后发现不适用，可以不照做。

## 技能选型

| 场景 | 技能 |
|---|---|
| 小需求 / 小 Bug（≤3 文件、单层、逻辑明确） | `fu-quick-dev` |
| 中等任务（需求基本清晰，不需要完整文档流） | `fu-standard-dev` |
| 全新功能 / 大型任务 | `fu-full-dev` |
| FairyGUI 界面与插件 | `fu-fgui-edit` |
| 需要驱动 Unity Editor | `fu-unity-cli-usage` |
| 配置表（Luban） | `fu-config-edit` |
| 提交前同步文档与知识 | `fu-doc-sync` |
| 代码评审自查 | `fu-code-review` |
| 把发现的规律沉淀成规则/踩坑 | `fu-rules-from-review` |

边界模糊时**宁可走重一档**。

## 反合理化

| 想法 | 事实 |
|---|---|
| "这个问题很简单，不用查技能" | 问题即任务。先查。 |
| "我很熟这个系统" | 熟悉提高设计质量，不是跳过流程的理由。 |
| "用户说直接开始" | "开始"不等于跳过澄清与方案确认。 |
| "我知道技能里写了什么" | 技能会演进。读当前版本。 |
| "这只是个小改动" | 小改动也会踩到准入三问里的坑。先查 traps。 |

## 落地后检查清单

- 改完 `.cs` → `bash .claude/verify-compile.sh`
- 提交前 → 列清单问用户确认（见 `rules/coding/git-conventions.md`）
- 踩到新坑 → 按 `.claude/memory/traps-authoring.md` 的准入三问决定是否入库
