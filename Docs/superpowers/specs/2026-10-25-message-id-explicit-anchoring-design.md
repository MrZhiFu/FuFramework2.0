# 设计：消息 ID 显式锚定与语义常量化

- 日期：2026-10-25
- 状态：已批准（2026-10-25）
- 范围：proto 源（5 文件）、ProtoExport 导出工具（两端模板）、gen-proto-registry.py、客户端/服务器生成物、网络模块日志微调、相关文档

## 1. 背景与动机

消息 ID 现状：`消息ID = (module << 16) + opcode`，opcode 由导出器**按声明顺序隐式 +1**（`MessageHelper.MessageIdHandler`，从 10 起），且生成时把算式**算成裸数值写死**（`ProtoBuffUnityHelper.cs:60`）。

三个真实痛点（用户确认全部存在）：

1. **抓包/查日志对不上号**：wire 上只有 `19660810` 这样的数字，查不出语义；
2. **读生成物/注册表发懵**：`[MessageId(19660810)]`、`Register<ReqHeartBeat>(655370)` 裸数字不可读；
3. **ID 漂移隐患**：隐式顺序分配下，在 proto 中间插入一条消息 → 后面所有消息 ID 全部漂移（兼容性地雷）。

参考方案（SLG 知识库 `04-网络模块/02、05 篇`）：协议号 = `(Module, Cmd)` 二元组，编号**显式写进 proto 枚举**（`TechLevelUp = 0;`），生成插件读枚举产出注册表——不存在漂移问题，枚举名即文档。本设计吸收其"显式锚定 + 生成注册"思想，但**不改二元组协议格式**（信封单 int ID 保持不变）。

## 2. 目标 / 非目标 / 反目标

**目标**

- 每条消息的 opcode 在 proto 源里**显式锚定**，消灭隐式漂移；
- 生成语义常量（模块枚举 + 消息 ID 常量），消息特性与注册表全部使用语义引用，可读、可 grep、可跳转；
- 抓包数字可速查（自动生成的对照表）；
- 现有全部 ID 数值**原样保留**（零兼容破坏）。

**非目标**

- 不改线上协议格式（信封仍是单 int ID，不动 14 字节包头）；
- 不引入 SLG 的 (moduleId, cmdId) 双字段信封；
- 不做 SLG 的 protoc 自定义插件（本项目导出器是纯正则解析，沿既有机制扩展）；
- 服务器注册体系（MessageMapping/HttpMessageMapping）不动。

**反目标（出现即失败）**

- 任何一条现有消息 ID 数值发生变化；
- 生成物需要手改才能工作（违反"生成物勿手改"惯例）；
- 运行时引入反射查表（铁律 4）。

## 3. 已定决策（用户拍板）

| 决策 | 结论 |
|---|---|
| 忘写 `option opcode` 的消息 | **报错强制**（导出中止并指出文件/消息名），一次迁移到位 |
| 日志增强 | **本次一起做**（范围见 §4.6） |
| 实体前缀词汇 | User/Player 保持，Role 留给权限系统（前置定案） |
| 参考来源 | SLG 知识库 02/05 篇；吸收显式锚定，拒绝二元组信封 |

## 4. 设计

### 4.1 proto 层：`option opcode` 显式锚定

每条**消息**（`IsMessage`：Req/Resp/Notify 前缀消息）显式声明 opcode，与已有的文件级 `option module` 对称：

```proto
// User_300.proto
option module = 300;

// 请求账号登录
message ReqUserLogin
{
  option opcode = 10;
  string UserName = 1; // 用户名
  ...
}
```

规则：

- **锚定对象仅限 `IsMessage`**：Req/Resp/Notify 消息必须标注；**非消息 DTO（如 `PlayerInfo`、`BagItem`）禁止标注** `option opcode`，出现即报错——DTO 无 ID 不占槽位，且防止 DTO 转正为 Req 时旧值静默生效；
- opcode 作用于**模块内**，全模块 ID = `(module << 16) + opcode`；
- 缺失 → 导出器**报错中止**，消息列出文件名与 message 名；
- 重复 → 报错中止（对齐字段 tag 的 `CheckVerifyMember` 行为）；唯一性校验范围见 §4.7；
- 取值范围 ≥10（沿用现状下限，强制），上限 65535（16 位空间）；
- Req 与 Resp **各自独立占用 opcode**（维持现状：本项目 Req/Resp 不共享 ID，配对靠 UniqueId 侧信道）。

### 4.2 导出器改造（Tools/ProtoExport）

**`MessageHelper.cs`**：

1. 新增 `OpcodePattern = @"option opcode = (\d+);"`；
2. `ParseMessage` 的逐行循环中，识别 `option` 开头的行：提取 opcode 存入 `MessageInfo.Opcode` 后跳过（当前该行会被误当字段解析，须先拦截）；
3. `MessageIdHandler` 改造为**校验器**：`IsMessage && Opcode` 缺失 → throw（含文件/消息名）；**非消息 DTO 带 `option opcode`** → throw；重复 → throw（范围见 §4.8）；不再自动分配（删除 `start++` 隐式逻辑）。

**`ProtoBuffUnityHelper.cs` / `ProtoBuffServerHelper.cs`**（两端模板同步）：

1. 特性参数从裸数值改为常量引用：`[MessageId(MessageIds.User.ReqUserLogin)]`；
2. 每个导出目录**额外生成一个 `MessageIds.g.cs`**（会被 `ProtoBufMessageHandler.Start()` 的整目录重建机制统一管理，符合"生成物勿手改"）：

```csharp
// <auto-generated/> 由 ProtoExport 生成，勿手改
namespace Hotfix.Game.Proto   // 服务器侧为 FuFramework.Proto.Proto
{
    /// <summary>模块号总表（与 proto 文件 option module 一一对应）</summary>
    public enum MessageModule
    {
        Inner_Basic = 2,
        Basic = 10,
        Common = 20,
        Bag = 100,
        User = 300,
    }

    /// <summary>消息 ID 语义常量：ID = (module << 16) + opcode</summary>
    public static class MessageIds
    {
        public static class User   // module 300
        {
            public const int ReqUserLogin  = ((int)MessageModule.User << 16) + 10; // 19660810
            public const int RespUserLogin = ((int)MessageModule.User << 16) + 11; // 19660811
        }
        // ... 每模块一个嵌套类
    }
}
```

- 模块枚举成员名取**包名/文件业务名**（User_300 → User；Basic_10 → Basic；Inner_Basic_2 → Inner_Basic）；
- 常量用 `((int)MessageModule.X << 16) + N` 算式（编译期常量，合法的特性参数），行尾注释保留数值——可读性双保险；
- 特性参数合法性与 ID 正确性由导出器自查：生成后重新解析生成物比对数值（或单元级断言）。

### 4.3 注册表生成器改造（Protobuf/gen-proto-registry.py）

- `RE_MSG_TYPE_ATTR`（`gen-proto-registry.py:82`，现只匹配 `(\d+)`）改为匹配标识符 `([\w.]+)`；
- 扫描消息类之前**先解析 `MessageIds.g.cs`**，建立 `常量路径 → 数值` 字典（如 `MessageIds.User.ReqUserLogin → 19660810`），消息类的 `[MessageId(标识符)]` 查表得数值；
- 查表失败（标识符不存在）→ 报错中止；
- 产出 `MessageRegistry.g.cs` 的注册行改为：`MessageIdRegistry.Register<ReqUserLogin>(MessageIds.User.ReqUserLogin);`

### 4.4 现值迁移（一次性）

5 个 proto 文件（module 2/10/20/100/300）的**全部 IsMessage 消息**按**当前导出物的实际数值**回填 `option opcode`（Basic 的心跳 10/11/12、User 的 10..19、Bag 的 10..19；Common/Inner_Basic 无消息体），保证迁移后 ID 数值零变化。

迁移完成的校验（**两端都要**）：
- 客户端：重跑导出后 `MessageRegistry.g.cs` 的 ID 数值与迁移前 diff 为空（仅常量引用形式变化）；
- **服务器：`Server/FuFramework.Proto/Proto/*.cs` 中 `[MessageId(...)]` 行的数值 diff 为空**——服务器运行期（`MessageProtoHelper` 启动建表）以该数值为收包分发依据，必须逐值核对。

### 4.5 服务器侧

- `ProtoBuffServerHelper.cs` 同步生成常量引用与 `MessageIds.g.cs`（命名空间 `FuFramework.Proto.Proto`）；
- **服务器运行时确实消费 `[MessageId]`**：`HotfixModule.cs:289` 与 `MessageProtoHelper.cs:140-172` 在启动期反射读取特性数值，构建 ID→类型收包分发表（`AllMessageDictionary` 等，撞号抛异常）。因本次 ID 数值零变化（§4.4 双端 diff 校验保障），运行时行为不变；
- 服务器注册体系（`MessageMapping`/`HttpMessageMapping` 按类型绑定）不动。

### 4.6 日志与速查（痛点 1）

- **收发日志格式微调**（`NetworkChannelBase.Send.cs:178` / `Receive.cs:134`）：ID 与类型名并置更醒目，如 `ReqUserLogin(19660810)`——类型名已存在（`msgObj.GetType().Name`），仅重排格式，不新增映射表；
- **速查表生成**：导出器额外产出 `MessageIds.md`（模块→号、每消息 ID→语义名对照，按模块分组）到 `Protobuf/` 目录，抓包时直接查。生成物惯例，勿手改。

### 4.7 跨文件全局唯一性校验（导出器 `Post()` 阶段）

现状一文件一模块（module 2/10/20/100/300 互异）但无机制强制。导出器在全部 proto 处理完的 `Post()` 阶段加两道校验，违反即报错中止：

1. `(module, opcode)` 二元组**跨文件全局唯一**（挡住 wire ID 撞号，不再依赖下游 gen-proto-registry 的 validate 或服务器启动期异常兜底）；
2. `module` 号**每文件唯一**、package 名每文件唯一（维持 1:1 惯例）。

### 4.8 服务器内置协议盲区（DiscoveryCenter）

`Server/FuFramework.Proto/BuiltIn/DiscoveryCenter.cs` 有 6 条**手写**内置消息（module = `short.MaxValue - 1` = 32766，特性内联算式），属服务器框架进程间协议，不在 proto 生成体系内。本次处理：

- **不纳入** `MessageModule`/`MessageIds` 生成（手写文件不适用生成物惯例，客户端抓包场景碰不到该段）；
- `MessageIds.md` 速查表尾部**注明盲区**：32766 段为服务器内置协议，不在生成范围。

## 5. 约束清单（builder 必须遵守）

1. 铁律：UniTask/无协程/无 LINQ/运行时无反射——常量类是编译期 const，天然满足；
2. 现有 ID 数值一个都不能变（迁移回填后 diff 校验）；
3. 所有新产物都是生成物（`.g.cs`、`.md`），模板改动集中在 `Tools/ProtoExport` 与 `gen-proto-registry.py`；
4. 特性参数必须是编译期常量（const int 满足）；
5. 两端生成物的常量必须来自同一份 proto（天然一致），不要在服务器侧引入第二事实源；
6. Windows 环境：批量文本改动警惕大小写（用 `-creplace`/perl，勿用大小写不敏感 replace）；改完编译验证（Unity `unity-cli` + 服务器 `dotnet build`）+ 重跑 `Proto2CsExport-All.bat ci`（**必须带 ci 参数**，否则 pause 假死）。
