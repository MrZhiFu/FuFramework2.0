# 01 · 一条消息的一生（全景数据流 + 网络频道）

> 配套图：[消息数据流图](../.archify/dataflow-message-lifecycle-20261019-222217/message-lifecycle.html) · [模块整体架构图](../.archify/architecture-network-overview-20261019-222217/network-overview.html)
> 本篇范围：先建立"一条消息从业务到网线再到业务"的整体地图，再讲清"网络频道（NetworkChannel）"这个贯穿全模块的核心概念。

---

## 一、What：一条消息是怎么"走一趟"的？

以你在 `WinPlayerList` 点登录、发出 `ReqLogin`、收到 `RespLogin` 为例，整条链路分发送、接收两个半程。

**发送半程（客户端 → 服务器）**

```
业务代码        WinPlayerList.LoginAsync()
                → 构造 ReqLogin（一个 C# 对象，proto 生成）
频道 Channel    SystemTcpNetworkChannel.Send(msg)
                → 业务只跟"频道"打交道
发送包头处理器   PacketSendHeaderHandler
                → 写"信封"：消息ID + 总长 + 压缩标志 + UniqueId（14 字节）
发送包体处理器   PacketSendBodyHandler
                → 把 C# 对象序列化成字节（proto）
Socket          SystemNetSocket → OS TCP → 网卡
                → 交给互联网
```

**接收半程（服务器 → 客户端，方向相反、处理器成对）**

```
网卡 → Socket 数据到达 → SystemNetSocket.ReceiveCallback
接收包头处理器   PacketReceiveHeaderHandler（读信封，知长度 → 粘包切分）
接收包体处理器   PacketReceiveBodyHandler（按消息 ID 反序列化成 RespLogin）
执行链表         m_waitingHandleMsgLkList（后台线程 AddLast、主线程 RemoveFirst）
派发             RPC 配对 / [NotifyMessageHandler] 订阅者
业务             LoginAsync 里 await 到了响应
```

**三个必须记住的认知：**

1. **为什么有"包头"和"包体"两段？** TCP 只保证字节流到达，不保证消息边界；包头是自制"信封"，写明"这条消息多长"，是切包的唯一依据（第 3 篇展开）。
2. **为什么收发各有两个处理器？** 信封（头）与信纸（体）读写分离、职责单一；压缩只作用于信纸。
3. **心跳在哪？** 不在业务流程里——是频道每 5 秒的自动行为（`ProcessHeartBeat`），第 4 篇讲。

---

## 二、Why：为什么要"频道"这一层？

**一句话：频道 = 一条通信线路的完整封装。** 类比打电话：**一通电话就是一个"频道"**——独立的线路、独立的心跳、独立的缓冲区、独立的一套处理器。当前客户端只开一条线；未来若有多线路需求（如聊天服），按同样的频道实例模式扩展（隔离能力保留在抽象里）。

为什么不直接用 `Socket`？三个理由：

| 理由 | 说明 |
|------|------|
| 1. **Socket 太原始** | 它只会读写"原始字节流"，游戏要的是"发一个 ReqLogin、收一个 RespLogin"。中间差的每件事（消息边界、序列化、心跳、断线判定）都由频道补齐 |
| 2. **多线路需要隔离** | 多条线路的缓冲区、心跳计时、处理器互不串扰——"每条线一个频道对象"天然实现（当前单线，扩展时按此模式加实例） |
| 3. **可替换性** | 业务只认识 `INetworkChannel` 接口；TCP 换 WebSocket 时，业务代码一行不改（第 5 篇/类图可见同一套接口两个实现） |

## 三、How：频道体系与频道的"一天"

### 3.1 频道体系（四个类的分工）

```
NetworkModule（门面："总开关"）
  │ 直接持有唯一频道：NetworkChannelBase
  │ 每帧驱动频道 Update()（收发轮询 + 心跳检查）
  ▼
INetworkChannel（接口："一通电话该会什么"的契约）
  ▼
NetworkChannelBase（频道的公共核心）
  ├── SystemTcpNetworkChannel（TCP 电话）
  └── WebSocketNetworkChannel（WebSocket 电话）
```

重要细节：**目录拆分只是物理组织，命名空间是扁平的**——`Framework/Network` 下全部 51 个文件声明同一个 `namespace Hotfix.Framework.Network`。移动文件不影响 `using`。

### 3.2 一个频道对象里装着什么

看 `INetworkChannel` 真实成员，按职责分四组：

| 分组 | 成员（节选） | 类比 |
|------|-------------|------|
| 线路 | `Socket`（`INetworkSocket`） | 电话线本身 |
| 协议装备 | 6 个处理器属性：`PacketSendHeaderHandler`、`PacketReceiveBodyHandler`、`MessageCompressHandler`… | 信封规则+拆信规则+压缩机 |
| 保活 | 心跳间隔与丢失计数（频道内部状态，由心跳处理器注入） | 每隔几秒"喂，还在吗？" |
| 能力 | `Connect()` / `Send<T>()` / `Call<TResult>()` / `Close()` | 拨号/说话/问话等答/挂断 |

### 3.3 频道的一天（真实代码三段式）

```csharp
// ① 开线：创建频道（模块内唯一，无名字），helper 负责装上处理器
NetworkModule.Instance.CreateChannel(new NetworkChannelHelper());
// ② 拨号
NetworkModule.Instance.Connect(new Uri($"tcp://{serverIp}:{serverPort}"));
// ③ 日常：Send = 说完不等；Call = 问话并 await 答复（第 6 篇）；④ 挂断 = DestroyChannel
```

③④ 之间所有的时间，是 `NetworkModule.OnUpdate` 每帧循环驱动频道：收 Socket 数据、发待发消息、查心跳——业务代码完全无感。
单频道模型下 `OnUpdate` 直接驱动唯一频道（`m_networkChannel?.Update(...)`），无集合遍历。

## 四、自测（随学随考）

### 题目

1. 发送半程依次经过：业务 → `___` → `PacketSendHeaderHandler` → `___` → `SystemNetSocket` → 网卡？（补出两个空）
2. 为什么收发的"处理器成对"？（提示：信封/信纸各一套）
3. "频道"存在的三个价值是什么？哪一条最重要（一到两句）？
4. `Framework/Network/` 下一堆子目录（`Channel/`、`Socket/`、`Handler/`、`Register/`…），它们的命名空间一样吗？说明了什么？
5. 一组频道对象里有哪四组东西？举出每组一个成员名。
6. `NetworkModule.OnUpdate` 在“频道尚未创建”时是怎么处理的？用户回调里创建/销毁频道会有集合失效风险吗？

### 答案

1. **`SystemTcpNetworkChannel`（频道）** 和 **`PacketSendBodyHandler`**。
2. 收发是方向相反同一套动作的镜像：写信封→读信封、写包体→读包体；职责分离（信纸压缩只作用于包体），同一套契约两端各一半。
3. Socket 太原始需要封装；多线路需要隔离；客户端只认接口，TCP/WS 可替换。**第 3 条最重要**——它让"换传输不换业务"成为可能。
4. 一样——全部 `namespace Hotfix.Framework.Network`（扁平命名空间）。说明目录只是物理分组、为导航服务的；移动文件不破坏 `using`。
5. 线路（`Socket`）、协议装备（`PacketSendHeaderHandler` 等处理器属性）、保活（心跳间隔与丢失计数的内部状态）、能力（`Connect/Send/Call/Close`）——任意四组均可。
6. `m_networkChannel?.Update(...)`——null 条件运算符静默跳过（频道 `Update` 内部还有未连接早退守卫）。单频道模型下模块只持一个字段、没有集合遍历，所以用户回调里创建/销毁频道不存在 `InvalidOperationException` 风险。
