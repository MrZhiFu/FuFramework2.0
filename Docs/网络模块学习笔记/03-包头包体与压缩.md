# 03 · 包头 / 包体与压缩（协议层）

> 本篇范围：14 字节"信封"每个字段为何存在、占用多大；`int`/`uint`/`byte` 与"占格"的区别；**字节序（本项目是大端）的实测真相**；压缩策略；空消息的特殊处理。

---

## 一、What：那个 14 字节的信封

发送侧写入顺序 = 接收侧读取顺序，这就是你和服务器之间的**协议契约**（`PacketSendHeaderHandler` 写、`PacketReceiveHeaderHandler` 读，字段成对存在）：

| 字节偏移 | 字段 | 长度 | 发送侧 | 接收侧 | 含义 |
|---------|------|------|--------|--------|------|
| 0 | `PacketLength` | 4（uint） | `WriteUInt(总长)` | `ReadUInt` | **总长**——切包依据 |
| 4 | `OperationType` | 1 | 心跳=1 / 普通=4 | `ReadByte` | 消息类别 |
| 5 | `ZipFlag` | 1 | 压缩=1 否则=0 | `ReadByte` | 包体是否压缩 |
| 6 | `UniqueId` | 4（int） | `WriteInt(msg.UniqueId)` | `ReadInt` | 唯一编号（RPC 配对钥匙，第 6 篇） |
| 10 | `Id` | 4（int） | 查注册表 | `ReadInt` | 消息 ID → 类型 |

尺寸配方就在构造里：`4 + 1 + 1 + 4 + 4 = 14`。

### 类型 vs 占格 vs 端序（三件独立的事）

- **类型**（`int`/`uint`/`byte`）＝"人怎么解释这些字节"；`int` 与 `uint` **都占 4 字节**，只差允许范围（`int` ±21 亿、`uint` 0~42 亿——长度用 `uint` 语义更诚实）。
- **占格**（`4/1/4…`）＝"在线上占几格"。**C# 里 `int` 恒为 `Int32` = 4 字节**（跨平台不变，不像 C++）。
- **端序**（大/小端）＝"这几个字节按什么顺序排"，见下节。

### 为什么是 `4+1+1+4+4`，而不是其他数字？

| 字段 | 为什么这个字节数 | 换更小的代价 |
|------|----------------|-------------|
| 长度 4 | 要能描述"自有最大消息"（`MaxPacketBodyLength=1 MiB`）；2 字节上限 64KB 会挡道；3 字节无原生类型，int 对齐省事 | 消息上限被卡死 |
| `Id` / `UniqueId` 各 4 | 与 `MessageIdRegistry`（键 int）、`MessageObject.UniqueId`（int）数据类型一致 | 全链路改类型，收益只是省几个字节/包 |
| 标志位各 1 | 它们只是 0/1 开关 | 与 OperationType 合并成一位可减 1 字节，牺牲可读与扩展 |

**结论：14 是"够用 + 对齐 + 留余量"的平衡点，没有魔法**——换成 13/10/20 都行，只要两端按同一张表写。协议不是"发现了 14 这个真理"，而是"你俩同意这么对表"。

### 定长而不是变长

包头定死 14 字节，而非像 proto 那样 varint 变长。变长省字节但收货时"不知道头在哪对完"；定长只需一个判断"够 14 字节了吗？"，完美嵌入第 2 篇"长度够了就切、不够就攒"。

## 二、Why：字节序——为什么同一个 4 字节会读出完全不同的值

`int` 占 4 字节，但 4 个字节按什么顺序摆有两种约定（`0x01020304` 为例）：

```
大端（最高位在前，人写字一样）：  [01][02][03][04]  → 0x01020304
小端（最低位在前，x86 内存）：    [04][03][02][01]  → 0x04030201（反了 4 亿！）
```

- **大端**：互联网协议（IP/TCP 头）的 `network byte order`，人类可读性好。
- **小端**：x86 CPU 的内存布局习惯。
- 两端约定不同 → 同一个字节序列读出完全不同的值 → 协议崩或"假死"。

### 本项目实测：统一大端（有代码为证）

不靠记忆（连老师都会记错），直接查 `Core/Extension/Common/BufferEx.cs`：

```csharp
WriteUInt / ReadUInt  → BinaryPrimitives.WriteUInt32BigEndian / ReadUInt32BigEndian
WriteInt  / ReadInt   → IPAddress.HostToNetworkOrder / NetworkToHostOrder
WriteUShort/ReadShort → *UInt16BigEndian / HostToNetworkOrder
```

**全员大端（网络字节序）**。再看服务器：`Server/.../ByteExtension.cs`、`SpanExtension.cs`、`ReadOnlySpanExtension.cs` 同样是 `Write/Read*BigEndian` 与 `HostToNetworkOrder`——**客户端与服务器全链路统一大端**。服务器 `ClientMessageEncoderHandler` 的五字段顺序与客户端逐字节一致（`PackageHeaderLength=14`）。

### 为什么不直接 `BitConverter.ToUInt32`？

`BitConverter` 按**平台默认序**（x86 上是**小端**）读——用它去读本项目（大端）写的包，读出的数值整个反了。正确姿势是三选一：`BinaryPrimitives.ReadUInt32BigEndian(...)`、`NetworkToHostOrder(...)`、或在不确定性环境先查 `BitConverter.IsLittleEndian`。

**对表原则：以代码为准，不信记忆；两端不必用同一个函数，只要产出同一字节布局。**

### 另一层字节序：protobuf

信封之下还有 proto 序列化层，protobuf 规范自带其内部约定（varint 小端优先），客户端与服务器都用 protobuf 标准库 → 自动一致。**两层字节序各异（包头大端 / pb 小端）但各自在层内两端统一，互不混用、彼此不冲突。**

## 三、How：发送侧写信、接收侧拆信、空消息的特殊通道

### 3.1 发送侧：一封信的制作（主线程，`PacketSendHeaderHandler.Handler<T>`）

```csharp
// ① 消息 ID：类型 → 查注册表（MessageIdRegistry）
Id = MessageIdRegistry.GetIdByType(messageObject.GetType());
// ② 序列化"信纸"：C# 对象 → proto 字节
messageBodyBuffer = SerializerHelper.Serialize(messageObject);
// ③ 压缩：信纸超过 512 字节且装了压缩器 → 压，并打 ZipFlag=1
if (messageCompressHandler != null && messageBodyBuffer.Length > LimitCompressLength)
{ IsZip = true; messageBodyBuffer = messageCompressHandler.Handler(messageBodyBuffer); }
// ④ 写信封：五字段依次进 14 字节缓存，总长 = 14 + 包体长
PacketLength = (uint)(PacketHeaderLength + messageLength);
destination.Write(m_cachedByte, 0, PacketHeaderLength);
```

随后频道依次调包体处理器把"信纸"写进同一流，`BeginSend` 整包发出。一条消息占 `14 + 包体长度` 字节。

### 3.2 接收侧：拆信（粘包问题的正解，`ProcessReceivedBytes`）

```
收到的一坨字节（可能是粘包/半包）→ 追加入 ReceiveState.Stream 蓄水池
  if (Position < Length) return;          // ② 半包：没凑够，攒着等下一批
  重置 Position=0，围绕信封切：
    ProcessPackHeader()  → 读信封 → 得 bodyLength → Reset(目标长)
    ProcessPackBody()    → 读包体 → ZipFlag 判解压 → 反序列化 → AddLast（入执行链表）
```

**关键的"攒够"判断**：`ProcessPackHeader` 成功后 `Reset(bodyLength, header)` 把蓄水池容量设为目标包体长；下一轮 `Position < Length` 就是"包体没到齐"的天然判断（半包自动攒、粘包自动切）。

### 3.3 空消息（包体长度 = 0）——一个必须当帧闭环的特例

空消息（如 `NotifyServerFullyLoaded {}`）只有 14 字节信封、没有信纸。`ProcessReceivedBytes` 里有一行看似"多余"的调用，**其实必须存在**：

```csharp
if (m_ReceiveState.IsEmptyBody)
{
    // 空消息（包体长度 = 0）：包头即整条消息，没有包体可等攒，
    // 当帧调 ProcessPackBody 解析入队并复位状态机后再返回（不能省略，否则消息丢失且状态机残留错位）。
    ProcessPackBody();
    return;
}
```

- 空消息没有"要等 data 的信纸"，信封读完即整条完成，**必须当帧解析入队并复位**（`ProcessPackBody` 末尾 `PrepareForPacketHeader()` 把状态机重置回"等下一个包头"）。
- 若"省略"这行：空消息永远不被反序列化（消息丢失）；且 ReceiveState 停留在"信封已读、未复位"状态，下一帧会拿残留的空消息头去切新数据 → **后续所有包错位**。
- 为什么不能"像普通消息一样留到下一帧处理"？因为 `if/else` 同帧互斥，普通消息靠"下一轮攒够包体再走 `if(PacketHeader!=null)` 分支"；空消息 Length=0 时这个两段式会立刻错位。

### 3.4 压缩的两个设计点

1. **信封永不压缩，信纸可选压缩**：如果信封也压了，接收方没法先读长度来切包——"长度"是切包与压缩的前置，压信封是死锁。
2. **压不压由发送方单方决定**（`>512` 才压），接收方只信 `ZipFlag` 一位 → **无状态自描述**：任何一封信靠自己信封独立处理，两端无需握手同步状态。

## 四、自测（随学随考）

### 题目

1. 消息体 100 字节，整条占多少字节？`PacketLength` 写几？
2. `int` 与 `uint` 哪个占的字节多？字节数由什么决定？
3. 为什么本项目信封的每个 4 字节字段都是大端？（试从 `BufferEx.cs` 举两处实现函数名）
4. 用 `BitConverter.ToUInt32` 读本项目包头，会发生什么？正确姿势是什么？
5. 为什么"信封永不压缩"？（说清那层死锁）
6. 空消息的 `ProcessPackBody()` 是"多余"的两行吗？删掉会发生什么？

### 答案

1. 整条 = 14 + 100 = **114 字节**；`PacketLength` 写 **114**（`14(信封)+100(信纸)`）。若写成 100，对端永远凑不齐，消息静默丢失。
2. **一样大**——`int` 与 `uint` 都是 32 位（4 字节）；差别仅在解释范围。字节数由类型决定（C# 里 `int` 恒=4），端序决定格内排列。
3. 因为 `BufferEx.cs` 的 `WriteUInt/ReadUInt` 用 `BinaryPrimitives.WriteUInt32BigEndian/ReadUInt32BigEndian`、`WriteInt/ReadInt` 用 `IPAddress.HostToNetworkOrder/NetworkToHostOrder`——统一大端（网络字节序）。服务器端 `ByteExtension/SpanExtension` 也是 `*BigEndian`，全链路一致。
4. `BitConverter` 按平台默认序（x86 上 = 小端）读，把大端写的包读出反序数值（例：想发 `0x18`=24，可能读成 `0x18000000`≈4 亿）→ 连接假死或消息损坏。正确姿势：`BinaryPrimitives.ReadUInt32BigEndian(...)` / `NetworkToHostOrder(...)` / 先查 `BitConverter.IsLittleEndian`。（本项目是 C# 服务端，引同一套扩展即可。）
5. 切包先读长度、甚至不确定是否要解压（ZipFlag 在信封里）——若信封也压了，接收方要先解压才能读长度，而解压又依赖先知道长度→死锁。所以信封必须健康、可直读；只有信纸可压。
6. **不是多余，是必须**。空消息（包体=0）没有信纸可等攒，必须当帧 `ProcessPackBody` 解析入队并复位状态机。删掉它会：① 空消息永远不被反序列化处理（静默丢失）；② ReceiveState 状态残留（信封已读未复位），下一帧用残留空头去切新数据 → 后续包错位。
