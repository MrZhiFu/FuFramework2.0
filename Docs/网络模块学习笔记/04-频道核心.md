# 04 · 频道核心（收发状态机 · 心跳 · 锁）

> 配套图：[心跳状态机](../../.archify/lifecycle-heartbeat-20261019-222217/heartbeat.html)
> 本篇把第 2、3 篇的零件装成一台完整机器：`NetworkChannelBase` 每帧 `Update` 一镜到底，加上心跳保活、断线判定，以及"锁的领地"全景。

## 一、What：`Update` 一镜到底

`NetworkChannelBase.Update`（`NetworkChannelBase.cs` 的 Update 方法）每个游戏帧把频道该干的活全排一遍：

```csharp
public virtual void Update(float deltaTime)
{
    // 先排水生命周期事件，再做活跃检查：频道 Close 后 IsOpen=false，若排水在检查之后，
    // 已入队的 Closed 事件将永远滞留队列（Update 不再被有效执行）。
    DrainLifecycleEvents();

    if (m_Socket == null || !IsOpen) return;   // ① 频道没活（无连接或会话已关）就歇着

    // 处理发送
    ProcessSend();                             // ② 发货

    if (m_Socket == null || !IsOpen) return;   // ③ 发送途中可能关闭了，再查一次

    // 处理心跳
    ProcessHeartBeat();                        // ④ 心跳检查（NetworkChannelBase.HeartBeat.cs 分部）

    // 处理接收
    ProcessReceived();                         // ⑤ 从执行链表取完整消息派发（收在心跳后：心跳判死 Close，当帧仍把已收消息派发完）

    // 驱动RPC逻辑更新，处理计时和超时移除任务
    m_rpcState.Update(deltaTime);              // ⑥ RPC 挂起表超时清扫
}
```

注意 ① 与 ③ 的两段 `IsOpen` 检查：发送过程中可能因错误把频道关闭，因此"边发边查、随时可停"。`IsOpen` 是会话闸门（区别于 `Connected` 的物理连接态：连接了但会话未启动/已关闭也不干活）。

## 二、Why：心跳为什么是"主动发起 + 被动复位"，死亡为什么不等于"半天没消息"

### 2.0 为什么必须自己做心跳：TCP 不管对端死没死（僵尸连接）

TCP 三承诺（可靠/有序/字节流）**不含生命体征**——往一条"对端已经消失"的连接里写字节，`Send` 可能照样"成功"（字节只是堆进了本机发送缓冲区，没有人取）。于是出现**僵尸连接**：一端已经不在了（进程被杀/断网/切后台被系统冻结网络），另一端却不知道，socket 还显示"已连接"。两端状态不一致，玩家表现为"点啥都没反应"。

游戏里最常见的四种成因：① 切微信/锁屏——系统冻结后台网络；② WiFi ↔ 4G 切换，网络路径改变；③ 运营商 NAT 映射过期（"你 ↔ 服务器"的门牌号被回收，回包再也进不来）；④ 服务器主动踢人（太久没收到客户端的包）。

**为什么 TCP 自己不管？** 操作系统自带的 TCP KeepAlive 探测默认 **2 小时**才动一次——对游戏毫无用处。应用层必须自己造"生命体征探测"——这就是心跳机制存在的根本原因（也是第 2 篇"TCP 三承诺不含心跳"的自然延伸）。

**本框架的短板与修复**（挂后台场景走查）：切后台 → Unity 停止调用 `Update` → 若按"每帧累加 dt"推进，心跳计时**停走**；回前台后要从旧值继续——再等最多 5 秒才补发第一个心跳，若连接已死，丢失计数还要再累计约半分钟（5 秒 × 5 次）才判死，期间玩家的所有 `Call` 都悬在超时里，"切个微信回来点啥都没反应"就是它。**已修复**（真实时钟探活）：流逝时长不再逐帧累加，改为记 `Time.realtimeSinceStartup` 时间戳、每帧取墙钟差值推进（`HeartBeatState.UpdateByRealTime()`）——挂起期间没有推进事件，回前台首帧的差值就是整段挂起时长，**立即"到点"补发心跳体检连接**（活连接正常回包清账，僵尸连接进丢失计数判死）；收包清账/连接重置会同步刷新时间戳基点，分段累计之和不变，"每 N 秒必发"的节奏不受影响。

玩家误以为"掉线 = 长时间没收包"。真实判定很不同（这也是把心跳做成以下结构的直接动机）：

- 客户端每 5 秒**主动发**一个心跳包（`SendHeartBeat` → `HeartBeatProvider.CreateHeartBeatReq()` → `Send`）。
- **收到任何字节**（不一定是心跳回包）→ `ReceiveCallback` 里 `Reset(false)`——**只清零丢失计数，不重置心跳流逝时长**（发送节奏独立运行、到点必发，与收没收流量无关）。
- 每发一次心跳却没收到任何回包 → `MissHeartBeatCount++`。
- **判死（主动方）**：`MissHeartBeatCount > 阈值` → `Close()`。阈值默认 5 来自心跳提供者 `HeartBeatProviderBase`（注册时经生成物覆盖），框架兜底默认是 10（`DEFAULT_MISS_HEART_BEAT_COUNT_BY_CLOSE`）。

含义：只有"我主动关心它、它却一直不吭声"才算死（网络真断了/对端挂了）；正常静默（比如没业务包但心跳正常）不会误判。**另有两条被动断开路径**：TCP 收到 `bytesReceived <= 0`（对端关闭）与网络错误事件→回调里 `Close()`——"断线判定"不止心跳一条。服务器一侧同样靠"多久没收到客户端的包"踢掉死连接——两边各自用自己的方式判断对方还活着。

`RpcState.Dispose` 的动机也在这里：**断线/销毁时必须让所有挂起的 RPC 请求以异常结束，否则 await 永久悬挂**（第 6 篇详细讲 `Cancel` vs `Clear`）。

## 三、How：发送 / 接收 / 心跳 / 锁

### 3.1 发送状态机（发货）

```
业务 Send → 队列 AddLast → 每帧 ProcessSend：
  ① 闸门（Length>0 或队列空 → return false）
  ② 从队头取消息 → ProcessSendMessage（写 14 字节包头 + 包体到 SendState.CacheStream）
  ③ 全部序列化完 → Position 归 0 → 子类 SendAsync()
  后台 SendCallback: Position += bytesSent
      · Position < Length → 续发（从新进度接着发）
      · Position == Length → Reset() 清箱
```
「续发从进度而不是从 0」——如果 `BeginSend` 起点写死 0，前 40 字节会被重复发送，对端按信封切出"缝合怪"，消息永久损坏（第 2 篇自测已推演）。

### 3.2 接收状态机（收数 + 切包 + 派发）

```
后台回调（线程池线程）：
  ReceiveCallback → ProcessReceivedBytes：
    蓄水池水位 += bytesReceived
    if Position < Length return（半包，攒）
    置 0 从头：ProcessPackHeader 读信封、ProcessPackBody 切包体/解压/反序列化/SetUniqueId(包头号)
  lock(m_handleMsgLock) 执行链表 m_waitingHandleMsgLkList .AddLast(完整消息对象)
主线程每帧：
  ProcessReceived: 锁内 First + RemoveFirst → 锁外
    ① is IHeartBeatMessage → 跳过（心跳回包不进业务派发）
    ② m_rpcState.TryReply（配对上→唤醒等待方）
    ③ NotifyMessageHandlerRegistry.TryDispatch（推送订阅者）
```
**接线点**：切包、反序列化全在后台回调线程；第二批数据靠"单飞行"串行（下一轮 `BeginReceive` 在上一轮回调的 `finally` 里才发起 → 同一时刻至多一轮接收在飞行），所以 `ReceiveState.Stream` 能被后台线程**无锁独占**（详见 3.4）。

### 3.3 心跳与断线（完整回路，见心跳状态机图）

```
ProcessHeartBeat（每帧，NetworkChannelBase.HeartBeat.cs 分部）：
   lock(m_HeartBeatLock):
     HeartBeatElapseSeconds += 真实时钟差值（UpdateByRealTime，挂后台回前台立即补发）
     到 5s 了？ → sendHeartBeat=true；计时清零；MissHeartBeatCount++   ← 先欠一次"缺勤"
   锁外（避免与 Close 锁十字死锁）:
     if sendHeartBeat: helper.SendHeartBeat()
       if miss>0: 触发 m_NetworkChannelMissHeartBeat 回调（连丢警告）
   锁内判定:
     MissHeartBeatCount > m_MissHeartBeatCountByClose → Close()   ← 判定死亡
两个"复位"把计数还原：
  - 收到任何包 → ReceiveCallback 里 lock(m_HeartBeatLock) Reset(false)（只清丢失计数，心跳流逝时长独立跑）
  - 连接一建立 → 计数归零
```

《[心跳状态机](../../.archify/lifecycle-heartbeat-20261019-222217/heartbeat.html)》展示了六个状态之间：计时 → 判间隔 → 发送 → 等待回包 →（收到任何包→复位 / 连续丢失→超阈值→Close→主动断开/错误→Close）。

### 3.4 锁的领地全景（每条数据/状态给谁摸、要不要锁）

| 数据 | 生产者 | 消费者 | 锁 | 原因 |
|------|--------|--------|----|------|
| `m_HeartBeatState`（计时/计数） | 主线程 `ProcessHeartBeat` | 后台 `ReceiveCallback`（Reset） | `m_HeartBeatLock` | 两线程都摸计时器 |
| `m_waitingHandleMsgLkList` | 后台回调（AddLast） | 主线程（RemoveFirst） | `m_handleMsgLock` | 收/派分属两线程 |
| `m_SendPacketPool` | 主线程入队 | 主线程取货 | `lock(m_SendPacketPool)` | 保守起见 |
| `ReceiveState.Stream` / `SendState.CacheStream` | 后台回调链（独占） | ——（不跨线程消费） | **无锁** | "单飞行"天然串行 |
| 生命周期事件队列 | 后台（Enqueue） | 主线程（Drain） | 锁内入队、锁外触发 | 跨线程 |
| `m_closeLock` | Close 专用 | —— | `m_closeLock` | 防关闭/心跳/发送交叉锁序 |

**一句话规则：跨线程共享才锁，单线程独占不设防。** 第 3 篇"空消息分支"之所以必须当帧 `ProcessPackBody` 复位，本质也是不让**状态机残留**破坏"独占无锁"的假设（残留的等待状态会把自己的列让给下一条错误数据）。

### 3.5 断线后：回到 Update 第 ② 行

`Close()` 之后会话闸门置位，下帧 Update 在 ② 处直接 `return` 歇业。`NetworkModule` 收到关闭事件广播给全游戏。**重连是在频道之外的业务决策**——频道只负责"状态机走完 → 通知世界我死了"，自己不反复重连；框架只补重连所需的三件"原语"，编排在 Game 层。（完整链路与踩坑实录见 **07 · 断线自动重连**。）

### 3.6 断线后：自动重连怎么串（三件套 + ReconnectManager）

频道只做一件事：把"我为什么死了"讲清楚——`Close(reason)` 按 `Active`（登出/销毁）或 `Lost`（心跳判死/收发异常/对端断开）标注，`NetworkClosedEventArgs.CloseReason` 随事件带出。重连编排只认 `Lost`。

```
断线 → Closed(Lost) → Game 层 ReconnectManager 分流：
        未进游戏（PlayerInfo 为空）→ 忽略（登录期由按钮兜底）
        被顶标记（NotifyPrompt Type=5）→ 弹提示回登录，不自动重连（防顶号乒乓）
        否则 → 弹"重连中"转圈框
              → ReconnectAsync(options, ct)      // 框架三件套之三：退避 {2,3,5,8,13}s × 5
              → 拨通 → GameSessionFlow 静默重登   // 挂阀门 → Call(ReqPlayerLogin) 建基线 → 恢复派发
              → 关全部窗口回主界面原地复活
        耗尽/失败 → "重连失败"框：【再试一次】(从拨号重头) / 【返回登录】(GameSessionFlow)
```

为什么"原地复活"不用动服务器：服务器断线即删会话，但玩家实体（Actor + 内存 State）有约 15 分钟事实宽限（`CheckIdle` 才回收）——重连重走登录协议认领的是同一份活着的数据，而非重建丢失。

三件套各自解决一个"难做对"的坑：`CloseReason` 让"主动登出"不至于触发重连死循环；`ConnectAsync` 把拨号结果变成可 await 的异常而非手写事件桥；`ReconnectAsync` 把退避周期与销毁重建封装成一次调用（取消语义：CT 取消立即停，不发起新一轮）。被顶与普通断线在客户端无法用 `CloseReason` 区分（服务器踢人只能标 `Lost`）——区分靠 `NotifyPrompt(Type=5)` 消息标记。

## 四、自测（随学随考）

### 题目

1. `Update` 里 ① 和 ③ 为什么都要查一次 `IsOpen`？
2. 心跳"死亡判定"到底看什么？和"很久没收到包"有什么区别？
3. `ReceiveState.Stream` 为什么可以不加锁？这个前提靠什么保证？
4. 命中"断线"（`Close`）时，挂起的 RPC 会怎样？（一句话）
5. 发送 `SendCallback` 里"续发从进度而不从 0"——如果写死 0 会怎样？

### 答案

1. ① 在干活前把关（频道未激活就歇着）；③ 在发送之后再次检查——因为发送过程可能触发错误把频道关闭（会话闸门关闭），此时若不拦，后半段的发送收尾会带着死连接跑，直接返回等下一帧。
2. 判定标准是**主动发的心跳没回**连续超过阈值（默认 5，来自心跳提供者的注册覆盖）触发 `Close`——"判死"看的是心跳的失联，不是"多久没业务包"。收到任意字节都会 `Reset(false)`（清零丢失计数、不重置心跳计时），正常静默不会误判；另有对端关闭与网络错误两条被动断开路径。
3. 因为"单飞行（in-flight）"：下一轮 `BeginReceive` 是在上一轮回调的 `finally` 里才发起的，同一时刻至多一轮接收在飞行 → 对 `ReceiveState.Stream` 的读写天然串行，只有一个后台线程摸它，故无需锁。举例：一旦改成同时发起多个 `BeginReceive`，这个无锁假设立刻崩塌。
4. 挂起的 RPC 全部被 `Cancel()`（`TrySetException(OperationCanceledException)`），`await` 抛取消异常而不是永久悬挂；同时关闭事件广播出去让业务弹重连。
5. 已发出的前 40 字节会被重复发送 → 对端按信封长度切包切出"缝合怪"（旧头+新尾）→ 消息损坏；最坏情况两帧拼接出**合法但错位的信封**，后续所有消息边界偏移、静默错乱。
