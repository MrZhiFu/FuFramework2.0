# 05 · 装配系统：零反射注册（铁律 4）

> 配套图：[频道类体系](../../.archify/architecture-channel-classes-20261019-222217/channel-classes.html) · [模块整体架构图](../../.archify/architecture-network-overview-20261019-222217/network-overview.html)
> 本篇回答：项目为什么"运行时杜绝反射"（铁律 4）、怎么把"发现"前移到生成期、三张表各自干嘛、以及装配时序和后注册覆盖。

---

## 一、What：零反射注册是什么

网络模块历史上有非常重型的运行期反射：`Assembly.GetTypes()` 扫全部程序集 → 读特性 → 按名字找方法 → `MethodInfo.Invoke`。**现在这套全都不要了**：

```
【生成期】（开发/构建时跑一次）
  Protobuf/gen-proto-registry.py
    ├── 扫描导出物：[MessageId(MessageIds.X.Y)] → 经 MessageIds.gen.cs 查表还原数值，得消息 ID 与类型
    ├── 扫描源码里的 [NotifyMessageHandler] → 直接产出静态绑定委托
    └── 扫描包处理器实现 → 直接 new
        │
        ▼ 产出：Register/AutoGen/MessageRegistry.gen.cs（编译期固化的"答案"）

【运行期】只做三件事，零扫描 / 零反射 / 零按名查找：
  查表（ID↔类型） / 绑定（实例↔委托） / 调用（直接调委托）
```

`MessageRegistry.RegisterAll()` 一页纸对应三张运行期表：

```
RegisterMessageIds()        → MessageIdRegistry        （ID↔类型唯一双向映射）
RegisterNotifyHandlers()    → NotifyMessageHandlerRegistry（BindNotify：消息类型→静态绑定委托）
RegisterExternalPacketHandlers() → NetworkChannelHelper（包处理器装配委托表）
```

## 二、Why：为什么要消灭反射（铁律 4 的动机）

| 代价 | 具体危害 |
|------|---------|
| AOT/热更裁剪 | iOS（IL2CPP）等裁剪器删掉"看着没被引用"的类型——而扫描对象恰是没被直接引用者，被删 → 运行时 GetType/Invoke 崩 |
| 启动开销 | `Assembly.GetTypes()` 逐类型特性判断 + 创建 MethodInfo/Activator，程序集越大越慢 |
| 反射调用慢 | `MethodInfo.Invoke` 比直接调用慢一个数量级，而它在每收一个包的热路径上 |
| 字符串耦合方法名 | 方法名写字符串，重构改名字 → 运行期静默失效，编译器不报错 |

前三项是性能/稳定性，第四项最阴险：改个方法名上线，消息悄悄不再处理。**生成期前移"发现"，把④变成编译期错误**（第 2 节 `internal` 那段：方法签名改了，`nameof` 和生成委托一起编译失败）。

### 为什么 `internal` 正好是"最小充分可见性"

生成委托 `static m => BagManager.Instance.OnX((X)m)` 在 `MessageRegistry` 类里，跨类调用 `BagManager.OnNotifyBagInfoChanged`：

- `private`/`protected`：生成代码既非本类也非子类 → 编译失败（生成脚本会报错中止）。
- **`internal`**：同程序集所有类型可见 → **能编译且最小暴露**（`Hotfix` 只有一个程序集，`Framework/Network` 与 `Game` 同汇编）。
- `public`：过度暴露——把实现细节变成对外契约，改签名要连外部调用方一起改。
- 什么情况才该 public？需要被**程序集外**显式调用（单元测试程序集、编辑器工具、被其他模块复用为 API）时才用 public；消息回调默认 internal 是正解。

### 为什么生成物用"一句话 lambda"而不是"具名静态方法"

二者**功能、性能完全等价**（C# 静态 lambda 会被编译成隐藏静态方法，零闭包、零 GC）。但对**生成物**而言 lambda 更优：无名 → 多个 handler 不撞方法名；一行浓缩 → 文件不膨胀；人瞄生成代码一眼就看到"这条注册指向谁"。具名方法要配唯一名（`Invoke_BagManager_NotifyBagInfoChanged` 之类），生成器复杂度与文件行数都上升，仅在"断点进 lambda 不方便"这类具体痛点时才有理由。

> 教训：`.gen.cs` 是生成物，**勿手改**——重跑 `gen-proto-registry.bat` 会把手动改动覆盖回生成器产物。想改生成形式只能改模板（`gen-proto-registry.py`）。

## 三、How：三张表 + 装配时序 + 后注册覆盖

### 3.1 表①：`MessageIdRegistry`（ID ↔ 类型）

每行都是生成物对注册表的静态调用：

```csharp
MessageIdRegistry.Register<ReqHeartBeat>(MessageIds.Basic.ReqHeartBeat);
MessageIdRegistry.Register<ReqUserLogin>(MessageIds.User.ReqUserLogin);
```

写入**双向字典**（`FuBidirectionalDictionary`），正反都查：

> opcode 由消息体内 `option opcode = N;` 显式锚定（缺失导出报错），ID 数值由此可长期稳定；语义常量见生成物 `MessageIds.gen.cs`。
> ID 构成：`(module << 16) + opcode`——module 占 int 高 16 位、opcode 占低 16 位（≤ 65535 即低位空间），32 位整数劈两半拼合，一个 int 同时编码"业务域 + 域内命令"。

```
反查（发包）：要发 ReqPlayerLogin，它的 ID 是多少？ → GetIdByType(typeof(ReqPlayerLogin)) = 19660816
正查（收包）：收到 ID=19660816，对应什么类型？ → GetTypeById(19660816) = RespPlayerLogin
心跳判断：    这个类型是心跳吗？              → is IHeartBeatMessage（接口运行期自描述）
```

发包与收包两侧：helper 的序列化写入反查 ID 写包头；helper 的包体解析正查类型反序列化。

### 3.2 表②：`NotifyMessageHandlerRegistry`（[NotifyMessageHandler] 推送绑定）

游戏代码声明"我要处理某条推送"——**声明即生效，无接口、无手动注册**：

```csharp
public sealed class BagManager : Singleton<BagManager>
{
    [NotifyMessageHandler(typeof(NotifyBagInfoChanged), nameof(OnNotifyBagInfoChanged))]
    internal void OnNotifyBagInfoChanged(NotifyBagInfoChanged msg) { /* 更新本地模型 */ }
}
```

生成器扫描源码，产出**静态捕获宿主的绑定委托**（`MessageRegistry.gen.cs`）：

```csharp
NotifyMessageHandlerRegistry.BindNotify(typeof(NotifyBagInfoChanged),
    static msgObj => Hotfix.Game.Manager_ToDelete.BagManager.Instance.OnNotifyBagInfoChanged((NotifyBagInfoChanged)msgObj),
    priority: 0);
//                                    宿主实例惰性触达（首次推送才创建）  方法编译期直调   参数强转（全部编译期，非运行时反射）
```

**多宿主 & 优先级**：同一消息可被**多个管理器**各自监听（每次标注产出一条独立 BindNotify，注册表按类型挂 List）；有模块间数据依赖时用 `Priority` 命名参数控制执行顺序——**数字小者先执行**，同优先级保持声明顺序：

```csharp
[NotifyMessageHandler(typeof(NotifyBagInfoChanged), nameof(OnBagForQuest))]               // 默认 0：先执行
[NotifyMessageHandler(typeof(NotifyBagInfoChanged), nameof(OnBagForUI), Priority = 5)]   // 5：排在默认之后（升序、小者先）
```

（想让 Q 先消费就让它保持默认 0 或更小值，把依赖它的消费者设为更大的 Priority。）

运行期只有两个动作：启动时 `BindNotify` 写表 → `SortByPriority()` 按优先级升序稳定排序一次（此后只读、派发零排序开销），收包时 `TryDispatch` 查表直调委托——全程无 `GetMethod`/`MethodInfo.Invoke`/字符串。改 `Priority` 数值后同样必须重跑生成脚本（编译期守卫比对键含优先级，会识别差异）。

**编译期守卫（忘跑脚本的最后防线）**：`Unity/Assets/Editor/FuFramework/Network/NotifyRegistryGuard.cs` 每次编译开始自动比对「业务源码声明」与「生成物 BindNotify 绑定」（键 = 消息类型.方法名:优先级 的计数），不一致即报错并列出缺失/多余条目；手动入口在菜单 `FuFramework/网络/重新生成推送注册表` 与 `FuFramework/网络/校验推送注册表一致性`。

两条配套契约：
- **宿主可达**：宿主必须继承 `Singleton<T>` 或提供 `static Instance`（生成器校验，不满足中止生成）——静态绑定要能拿到实例；
- **仅服务 Notify**：特性构造期校验消息类型必须实现 `INotifyMessage`——Resp 由 `Call` 的 RPC 配对消费，不进派发。

**派发阀门（基线未就绪窗口期）**：推送多为增量更新，依赖业务先建立数据基线。
`NetworkModule` 门面三方法：`SuspendNotifyDispatch()`（挂起：推送进缓冲队列，上限 1024 条、超出丢最旧+警告）→ 拉取全量 →
`ResumeNotifyDispatch()`（按到达顺序回放）；`ClearNotifyBuffer()`（登出/切号清缓冲防串号）。
（门面转发到注册表本体 `NotifyMessageHandlerRegistry.SuspendDispatch/ResumeDispatch/ClearBuffer`；挂在 `WinPlayerList.PlayerLoginAsync` 的基线窗口。）

**类图与接口现状**：真多态接口同居实现（`Channel/`、`Socket/`），消息契约接口集中于 `Interface/`（`IRequestMessage`+泛型/`IResponseMessage`/`INotifyMessage`/`IHeartBeatMessage`），**信封读写内置于 helper**（包处理器体系已随 Handler 目录删除退役——仅存的跨层对象是游戏侧心跳提供者 `HeartBeatProvider`，经生成物注册）。《[频道类体系](../../.archify/architecture-channel-classes-20261019-222217/channel-classes.html)》（注：该图绘制于缩接口前，接口形态为历史版本）。

### 3.3 表③：`NetworkChannelHelper`（信封读写 + 外部装配）

`Initialize` 做两件事：

```csharp
public void Initialize(INetworkChannel netChannel)
{
    m_networkChannel = netChannel;          // ① 信封读写器就位（序列化写入/包头解析/包体反序列化均为 helper 内置）
    foreach (var registrar in sr_externalPacketHandlerList)   // ② 显式注册的装配委托
        registrar.Invoke(m_networkChannel);
}
```

生成物往 ② 追加（`RegisterExternalPacketHandlers`）：

```csharp
NetworkChannelHelper.RegisterExternalPacketHandler(channel =>
{
    channel.RegisterHeartBeatProvider(new Hotfix.Game.Network.HeartBeatProvider());
});
```

### 3.4 心跳为什么没有兜底

心跳提供者**不在框架内**，根因是**依赖方向**：
心跳消息 ReqHeartBeat 是 proto 生成物，位于 Game 层——Framework 不引用 Game，框架无法构造心跳包。

因此基类 `HeartBeatProviderBase` 为 **abstract**（`CreateHeartBeatReq()` 抽象成员，编译期强制游戏侧实现），
游戏侧 `HeartBeatProvider` 是唯一实现、也是心跳机制的实际生效点（复用单个 ReqHeartBeat 实例，每次仅覆盖 Timestamp/UniqueId）。

> 历史教训（反射时代）：原实现扫描会同时命中基类与派生类，且基类排在派生类之后 → **基类生效**，
> 而基类构造方法抛 `NotImplementedException` → 心跳必炸；当时靠游戏侧手动补注册续命。
> 生成式注册 + abstract 基类把这条坑彻底填平：漏实现活不过编译，漏注册生成器会检测。

### 3.5 一条真实启动链路（登录）

```
启动：      NetworkModule.OnInit 内联注册表初始化 → RegisterAll() → 三张表就位
点击登录：  CreateChannel(new NetworkChannelHelper())
               → helper.Initialize(channel) → 信封读写就位 + 生成物注册的游戏心跳提供者
Send：查表①拿 ID → 写信封 → 写包体 → 异步发出（第 2/3 篇链路）
收 RespPlayerLogin：  读信封拿 ID → 查表①得类型 → 反序列化 → AddLast → 主线程派发（第 6 篇 RPC）
```

## 四、自测（随学随考）

### 题目

1. 为什么放弃 `Assembly.GetTypes()` 全程序集扫描？（四个理由里说两个以上）
2. 生成委托相比 `MethodInfo.Invoke` 多拿到什么好处？（两条即可）
3. 新增一个 `[NotifyMessageHandler]` 方法后不重跑 `gen-proto-registry.bat` 会怎样？
4. 心跳提供者为什么没有"框架兜底"，这个设计靠什么保证不缺心跳？
5. 为什么目标方法必须 `internal/public`，而不能是 `private`？
6. 手改 `.gen.cs` 会有什么后果？想改生成形式该改什么？

### 答案

1. ① AOT/热更裁剪会删掉"看起来没被引用"的类型，扫描对象恰是这类；② 启动扫描慢；③ `MethodInfo.Invoke` 比直接调用慢一个数量级、在热路径上；④ 方法名写字符串、改名字静默断链（且这四条里 ③/④ 尤其致命）。
2. ① 编译期类型安全：handler 类型、方法名、参数强转全在编译期钉死，改方法签名 → `nameof` 和生成委托一起编译失败；② 直接调用性能：`(BagManager)handler` 是编译期强转 + 一次直接 `callvirt`，无 Invoke 反射派发；③ AOT 友好：编译器能看到明确调用点，不删。
3. 编译期守卫兜底：忘跑 `gen-proto-registry` 时，NotifyRegistryGuard 会在下次编译时报错并列出缺失/多余绑定——不再"静默失效"。只有在绕开守卫（或守卫未刷新）的情况下，推送到达时 `TryDispatch` 查无绑定才打警告后**丢弃**（服务器不会补发）。所以改完特性标注仍要重跑生成器，守卫只是把"忘了跑"变成编译期可见的报错。
4. 依赖方向决定：心跳消息 ReqHeartBeat 在 Game 层，框架不引用 Game 无法构造——基类 `HeartBeatProviderBase` 为 abstract（`CreateHeartBeatReq()` 抽象成员编译期强制），游戏侧 `HeartBeatProvider` 由生成物自动注册，是唯一实现与实际生效点。
5. 生成委托在 `MessageRegistry`（另一个类）里调用：`private` 仅本类可见、`protected` 仅本类与子类可见，都无法从生成代码访问 → 必须 `internal`（同程序集）或 `public`（跨程序集，不必要的暴露）。这是"最小充分可见性"。
6. 重跑生成器会把手动改动覆盖回 lambda——手改不持久且与"自动生成"原则冲突。想改生成形式应改 `Protobuf/gen-proto-registry.py` 模板（如把 lambda 换成具名方法需处理多 handler 方法名冲突）。
