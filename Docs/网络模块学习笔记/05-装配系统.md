# 05 · 装配系统：零反射注册（铁律 4）

> 配套图：[频道类体系](../.archify/architecture-channel-classes-20261019-222217/channel-classes.html) · [模块整体架构图](../.archify/architecture-network-overview-20261019-222217/network-overview.html)
> 本篇回答：项目为什么"运行时杜绝反射"（铁律 4）、怎么把"发现"前移到生成期、三张表各自干嘛、以及装配时序和后注册覆盖。

---

## 一、What：零反射注册是什么

网络模块历史上有非常重型的运行期反射：`Assembly.GetTypes()` 扫全部程序集 → 读特性 → 按名字找方法 → `MethodInfo.Invoke`。**现在这套全都不要了**：

```
【生成期】（开发/构建时跑一次）
  Protobuf/gen-proto-registry.py
    ├── 扫描 proto → 消息 ID 与类型、心跳类型
    ├── 扫描源码里的 [MessageHandler] → 直接产出强类型委托
    └── 扫描包处理器实现 → 直接 new
        │
        ▼ 产出：Register/AutoGen/ProtoMessageRegistry.g.cs（编译期固化的"答案"）

【运行期】只做三件事，零扫描 / 零反射 / 零按名查找：
  查表（ID↔类型） / 绑定（实例↔委托） / 调用（直接调委托）
```

`ProtoMessageRegistry.RegisterAll()` 一页纸对应三张运行期表：

```
RegisterMessageIds()             → ProtoMessageIdRegistry        （ID↔类型双向字典 + 心跳集合）
RegisterMessageHandlerMethods()  → ProtoMessageHandlerRegistry（类型→[MessageHandler]方法清单+委托）
RegisterExternalPacketHandlers() → DefaultNetworkChannelHelper（包处理器装配委托表）
```

## 二、Why：为什么要消灭反射（铁律 4 的动机）

| 代价 | 具体危害 |
|------|---------|
| AOT/热更裁剪 | iOS（IL2CPP）等裁剪器删掉"看着没被引用"的类型——而扫描对象恰是没被直接引用者，被删 → 运行时 GetType/Invoke 崩 |
| 启动开销 | `Assembly.GetTypes()` 逐类型特性判断 + 创建 MethodInfo/Activator，程序集越大越慢 |
| 反射调用慢 | `MethodInfo.Invoke` 比直接调用慢一个数量级，而它在每收一个包的热路径上 |
| 字符串耦合方法名 | 方法名写字符串，重构改名字 → 运行期静默失效，编译器不报错 |

前三项是性能/稳定性，第四项最阴险：改个方法名上线，消息悄悄不再处理。**生成期前移"发现"，把④变成编译期错误**（第 2 节 `internal` 那段：方法签名改了，`nameof` 和生成委托一起编译失败）。

### 为什么 `internal` 正好是"最小充分可见性"

生成委托 `static (handler,m) => ((BagManager)handler).OnX((X)m)` 在 `ProtoMessageRegistry` 类里，跨类调用 `BagManager.NotifyBagInfoChanged`：

- `private`/`protected`：生成代码既非本类也非子类 → 编译失败（生成脚本会报错中止）。
- **`internal`**：同程序集所有类型可见 → **能编译且最小暴露**（`Hotfix` 只有一个程序集，`Framework/Network` 与 `Game` 同汇编）。
- `public`：过度暴露——把实现细节变成对外契约，改签名要连外部调用方一起改。
- 什么情况才该 public？需要被**程序集外**显式调用（单元测试程序集、编辑器工具、被其他模块复用为 API）时才用 public；消息回调默认 internal 是正解。

### 为什么生成物用"一句话 lambda"而不是"具名静态方法"

二者**功能、性能完全等价**（C# 静态 lambda 会被编译成隐藏静态方法，零闭包、零 GC）。但对**生成物**而言 lambda 更优：无名 → 多个 handler 不撞方法名；一行浓缩 → 文件不膨胀；人瞄生成代码一眼就看到"这条注册指向谁"。具名方法要配唯一名（`Invoke_BagManager_NotifyBagInfoChanged` 之类），生成器复杂度与文件行数都上升，仅在"断点进 lambda 不方便"这类具体痛点时才有理由。

> 教训：`.g.cs` 是生成物，**勿手改**——重跑 `gen-proto-registry.bat` 会把手动改动覆盖回生成器产物。想改生成形式只能改模板（`gen-proto-registry.py`）。

## 三、How：三张表 + 装配时序 + 后注册覆盖

### 3.1 表①：`ProtoMessageIdRegistry`（ID ↔ 类型）

每行都是生成物对注册表的静态调用：

```csharp
ProtoMessageIdRegistry.Register<ReqHeartBeat>(655370, EMessageKind.Request | EMessageKind.HeartBeat);
ProtoMessageIdRegistry.Register<ReqLogin>(19660810, EMessageKind.Request);
```

写入**双向字典**（`FuBidirectionalDictionary`），正反都查：

```
反查（发包）：要发 ReqLogin，它的 ID 是多少？ → GetReqMessageIdByType(typeof(ReqLogin)) = 19660810
正查（收包）：收到 ID=19660810，对应什么类型？ → GetRespTypeById(19660810) = RespLogin
心跳判断：    这个类型是心跳吗？              → IsHeartbeat(type)（HashSet，O(1)）
```

发营收两端各用一侧：`DefaultPacketSendHeaderHandler` 反查 ID 写包头；`DefaultPacketReceiveBodyHandler` 正查类型反序列化。

### 3.2 表②：`ProtoMessageHandlerRegistry`（[MessageHandler] 方法 + 强类型委托）

游戏代码声明"我要处理某条推送"：

```csharp
[MessageHandler(typeof(NotifyBagInfoChanged), nameof(NotifyBagInfoChanged))]
internal void NotifyBagInfoChanged(NotifyBagInfoChanged msg) { /* 更新本地模型 */ }
```

生成器扫描源码，产出**强类型委托**（`ProtoMessageRegistry.g.cs`）：

```csharp
static (handler, message) => ((Hotfix.Game.Manager_ToDelete.BagManager)handler).NotifyBagInfoChanged((NotifyBagInfoChanged)message)
//                       handler 类型强转       方法名编译期直调       参数强转（都是编译期，非运行时反射）
```

运行时 `ProtoMessageHandlerRegistry.Add` 只做"绑定"（`MessageHandlerAttribute.Bind(handler, 委托)`），收包时 `GetHandlers` 复制到复用缓冲 → 逐个 `handler.Invoke()` 直接调委托——全程无 `GetMethod`/`MethodInfo.Invoke`/字符串。

**类图标出接口层与实现**：包处理器接口在 `Handler/Interface/`，默认实现在 `Handler/`；频道接口与实现同居 `Channel/`，套接字同居 `Socket/`（接口跟随实现放置）。《[频道类体系](../.archify/architecture-channel-classes-20261019-222217/channel-classes.html)》。

### 3.3 表③：`DefaultNetworkChannelHelper`（包处理器装配）

`Initialize` 装配顺序（后写覆盖先写）：

```csharp
public void Initialize(INetworkChannel netChannel)
{
    RegisterDefaultHandlers();                     // ① 框架默认 7 个（收发头体/心跳/压解压）
    RegisterCustomHandlers();                      // ② 派生类钩子（可重写补充）
    foreach (var registrar in sr_customHandlerRegistrars)   // ③ 显式注册的装配委托
        registrar.Invoke(m_networkChannel);
}
```

生成物第三块往 ③ 追加（`RegisterExternalPacketHandlers`）：

```csharp
DefaultNetworkChannelHelper.AddCustomHandlerRegistrar(channel =>
{
    channel.RegisterHeartBeatHandler(new Hotfix.Game.Network.PacketHeartBeatHandler());
});
```

### 3.4 后注册覆盖（心跳链的运行时意义）

`RegisterHeartBeatHandler` 是"直接赋值覆盖"：

```
① 框架兜底： new DefaultPacketHeartBeatHandler()（Handler() 抛 NotImplementedException）
② 生成物追加：new PacketHeartBeatHandler()（返回 ReqHeartBeat）
最终生效 = ②（后注册者覆盖）
```

这条链就是 1~4 站评审过四轮的命名的运行时依据：`Base 兜底 → Game 具体实现`，不是风格洁癖，而是装配机制的必然结果。

### 3.5 一条真实启动链路（登录）

```
启动：      NetworkModule.OnInit 内联注册表初始化 → RegisterAll() → 三张表就位
点击登录：  CreateChannel(new DefaultNetworkChannelHelper())
               → helper.Initialize(channel) → ⑦ 默认处理器 + 生成物追加的游戏心跳
Send<ReqLogin>：查表①拿 ID → 写信封 → 写包体 → 异步发出（第 2/3 篇链路）
收 RespLogin：  读信封拿 ID → 查表①得类型 → 反序列化 → AddLast → 主线程派发（第 6 篇 RPC）
```

## 四、自测（随学随考）

### 题目

1. 为什么放弃 `Assembly.GetTypes()` 全程序集扫描？（四个理由里说两个以上）
2. 生成委托相比 `MethodInfo.Invoke` 多拿到什么好处？（两条即可）
3. 新增一个 `[MessageHandler]` 方法后不重跑 `gen-proto-registry.bat` 会怎样？
4. 游戏侧心跳靠什么机制"胜过"框架兜底？
5. 为什么目标方法必须 `internal/public`，而不能是 `private`？
6. 手改 `.g.cs` 会有什么后果？想改生成形式该改什么？

### 答案

1. ① AOT/热更裁剪会删掉"看起来没被引用"的类型，扫描对象恰是这类；② 启动扫描慢；③ `MethodInfo.Invoke` 比直接调用慢一个数量级、在热路径上；④ 方法名写字符串、改名字静默断链（且这四条里 ③/④ 尤其致命）。
2. ① 编译期类型安全：handler 类型、方法名、参数强转全在编译期钉死，改方法签名 → `nameof` 和生成委托一起编译失败；② 直接调用性能：`(BagManager)handler` 是编译期强转 + 一次直接 `callvirt`，无 Invoke 反射派发；③ AOT 友好：编译器能看到明确调用点，不删。
3. 该类型在 `ProtoMessageHandlerRegistry` 的注册表里"未登记"，`Add` 时打 `LogError` 并 `return`——该处理器类型收不到任何消息，行为上是"静默失效 + 一条日志提示重新生成"。
4. 「后注册覆盖」+ 装配顺序：`RegisterDefaultHandlers` 先装配框架兜底，生成物 `AddCustomHandlerRegistrar` 后追加游戏实现；`RegisterHeartBeatHandler` 直接赋新值，后写覆盖先写 → 最终生效的是游戏实现。
5. 生成委托在 `ProtoMessageRegistry`（另一个类）里调用：`private` 仅本类可见、`protected` 仅本类与子类可见，都无法从生成代码访问 → 必须 `internal`（同程序集）或 `public`（跨程序集，不必要的暴露）。这是"最小充分可见性"。
6. 重跑生成器会把手动改动覆盖回 lambda——手改不持久且与"自动生成"原则冲突。想改生成形式应改 `Protobuf/gen-proto-registry.py` 模板（如把 lambda 换成具名方法需处理多 handler 方法名冲突）。
