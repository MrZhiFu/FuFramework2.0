# 07 · 断线自动重连（会话的抢救与复活）

> 本篇范围：断线后客户端自动发生的完整链路；框架"三件套"各堵住什么坑；Game 层怎么编排"转圈框 → 重拨 → 静默重登 → 原地复活"；被顶号怎么识别；以及落地过程中踩过的 5 个**运行时才暴露**的坑。
> 前置：04 篇（频道核心·心跳与断线判定）、06 篇（RPC 与业务接入）。

---

## 一、What：断线后自动发生的完整链路

玩家正在主界面，网断了（拔线/服务器重启/切后台过久）。客户端**无人按任何按钮**，接下来自动发生：

```
TCP 断开 / 心跳判死
   ↓ NetworkChannelBase.Close(ENetworkCloseReason.Lost)   ← 「异常断线」标注
NetworkClosedEventArgs（携带 CloseReason）广播
   ↓ ReconnectManager.OnNetworkClosed 分流（顺序敏感，见 3.2）
非 Lost（主动登出/销毁）→ 忽略
未进游戏（PlayerInfo.Id ≤ 0）→ 忽略（登录期由按钮兜底）
被顶标记 → 弹"账号已在其他设备登录"→ 登出，不重连
   ↓ 否则
弹「重连中」转圈框（WinReconnecting，全屏模态）
   ↓ NetworkModule.ReconnectAsync（退避 {2,3,5,8,13}s × 5 次）
每轮：销毁旧频道 → 重建 → ConnectAsync 拨号
   ↓ 拨通
GameSessionFlow.LoginFlowAsync 静默重登（挂阀门 → Call 建基线 → 恢复派发）
   ↓
关闭全部窗口 → 重新打开主界面 —— 原地复活，不弹回选角界面
   （若 5 次耗尽）→「重连失败」框：【再试一次】从拨号重头 /【返回登录】GameSessionFlow.LogoutFlowAsync
```

一句话：**频道负责"死得明白"（标注死因），Game 层负责"救得回来"（编排复活）**。

---

## 二、Why：几个关键设计决策

### 2.1 为什么"原地复活"不需要动服务器

查证结论（读服务器源码）：**TCP 断开时服务器立刻删除会话**（`SessionManager.Remove`），但**玩家实体（Actor + 组件 + 内存 State）不随断线销毁**——"登出后再闲置 15 分钟"才被全局定时器回收。期间客户端重连走全新 `ReqPlayerLogin`，`ActorMap.GetOrAdd` 命中**同一个 Actor、同一份内存数据**——重登认领的是活着的会话，不是重建丢失的数据。

所以"原地复活"在客户端做完就够了。超过 15 分钟 Actor 被回收也不怕：重登后从 Mongo 重读最后落库数据，照样进游戏（数据回档到最后落库点，可接受）。

### 2.2 为什么必须区分 `Active` / `Lost`

`Close()` 不带原因的话，**主动登出和异常断线在业务层长得一模一样**——重连编排若一律重拨，玩家点"退出登录"就进入"登出 → 判死 → 自动重连 → 弹回游戏"的死循环。因此 `Close(ENetworkCloseReason reason)` 贯通全部调用点：主动路径（登出/销毁/重建清扫）传 `Active`，被动路径（心跳判死/收发异常/对端断开）传 `Lost`，随 `NetworkClosedEventArgs.CloseReason` 广播。**重连编排只认 `Lost`**。

### 2.3 为什么被顶号不能靠断线原因识别

被顶 = 服务器踢人，客户端只能走被动路径标 `Lost`——**与普通断线在断线原因上无法区分**。幸好服务器踢人前会先推一条 `NotifyPrompt`（Type=5"账号已在其他设备登录"）。客户端收到即立"被顶标记"，紧随其后的 `Closed(Lost)` 读到标记 → **不重连**，弹提示回登录。

不做这个标记的后果：被顶的玩家被自动"抢回来"，且两端都是本客户端时来回顶（乒乓）。而 `CloseReason` 里**没有**"被踢"枚举值——它天然归 `Lost`，这个区分只能靠应用层消息。

### 2.4 为什么登录期不自动重连（一个判空陷阱）

直觉写法是 `if (PlayerManager.Instance.PlayerInfo == null) return;`——但 `PlayerManager` **构造函数里就 `PlayerInfo = new PlayerInfo()`**（空对象，非 null），判空永远不成立 → 登录期拨号失败也触发重连 → 无限退避。正确判据：`PlayerInfo.Id > 0`（Id 仅在登录成功赋值后才非零）。详见踩坑实录 §四.1。

## 三、How：框架三件套 + Game 层编排

### 3.1 框架三件套（`Framework/Network`）

| 件 | API | 堵住的坑 |
|---|---|---|
| 关闭原因 | `Close(ENetworkCloseReason)`；`NetworkClosedEventArgs.CloseReason` | 主动登出被误重连（死循环）；业务层不用再猜"为什么断" |
| 可等待拨号 | `ConnectAsync(address, cancellationToken, timeoutMs)` | `Connect()` 发完即忘，业务要自己订阅两个事件写一次性桥；现在一行 await，超时/失败以异常返回 |
| 退避重拨 | `ReconnectAsync(ReconnectOptions, ct)` | 退避节奏、销毁重建、重试计数封装成一次调用；耗尽抛 `TimeoutException` |

三件套的共同点：**只提供"难以做对的原语"，不做策略**（退避序列是参数、收尾交给调用方）——策略性的东西留在 Game 层，等第二个使用场景出现再考虑下沉。

### 3.2 Game 层编排（`ReconnectManager`）

订阅 `Closed` 事件的**分流顺序敏感**：先查原因（非 Lost 忽略）→ 再查是否进过游戏（`Id ≤ 0` 忽略）→ 再查被顶标记 → 最后查重入（`m_isReconnecting`，重连中再断线由退避循环内部消化）。四道闸都过才启动重连事务。

重连事务（`StartReconnectFlow`）的三个出口——**成功**（CloseAll → 开主界面）、**失败**（CloseAll → 弹"重连失败"框）、**取消**（LogoutFlowAsync 回登录）——每一个都以 `CloseAll` 收尾，转圈框在所有出口必然被关（不存在"二次关闭"的空间，见踩坑 §四.4）。

### 3.3 会话流（`GameSessionFlow`：进/出对称）

- `LoginFlowAsync(playerId, ct)`：挂阀门 → `Call(ReqPlayerLogin)` 建全量基线 → 恢复派发；失败收尾（清缓冲 + 解除挂起）在内部，异常上抛。**重入防护**：同一时间只允许一个登录事务。
- `LogoutFlowAsync()`：终止重连 → 清玩家状态 → 清推送缓冲 → 关频道（`Active`）→ **卸载主场景** → 关全部窗口 → 回登录界面。卸载是必须的：`LoadScene` 对已加载场景直接抛"不能重复加载"，不卸则再登录当场炸。
- **令牌分工**：登录网络请求段用调用方的 Token（选角窗口关闭 = 放弃登录）；登录成功后的后续链（场景加载/开主界面）用 `GameSessionFlow.TransactionToken`（事务自有生命周期——窗口在事务中途 Close，其 Token 取消，不能沿用）。

### 3.4 边界情况速查

| 情况 | 行为 |
|---|---|
| 断线发生在登录期 | 不自动重连（Id ≤ 0 判定），玩家按钮兜底 |
| 重连拨通但 Actor 已被回收（>15min） | 正常重登，服务器从 Mongo 重读，无需客户端特判 |
| 重连期间再次断线 | `m_isReconnecting` 重入防护，退避循环内部消化 |
| 重连期间被顶号 | 重登成功即顶掉对方（服务器顶号语义）；对方若也在游玩中则走它的被顶分支 |
| 切后台超长（心跳判死堆积） | 真实时钟心跳回前台立即判死 → 进重连流程，退避序列自然吸收 |

## 四、踩坑实录：5 个运行时才暴露的坑

这一节是本篇最值钱的部分——**全部是编译期看不见、跑起来才炸的**。

### 坑 1：判空失效，登录期疯狂重连

`PlayerManager` 构造就 `PlayerInfo = new PlayerInfo()`，`== null` 判定**永远不成立** → 登录期拨号失败也触发重连。**教训：判定"已登录"要用业务字段（Id > 0），不能依赖"对象是否为 null"——尤其当对象由构造预创建时。**

### 坑 2：超时后的清理跑在了错误的线程

`ConnectAsync` 超时由 `CancellationTokenSource.CancelAfter` 的**线程池 Timer** 触发 → `await` 在线程池线程恢复 → `finally` 里的 `EventModule.Unsubscribe` 跨线程（事件池仅主线程）刷屏报错。**修复：捕获异常后 `await UniTask.SwitchToMainThread()` 切回主线程再退订，最后重抛。教训：await 的恢复线程取决于"谁唤醒了它"——Timer 唤醒就在 Timer 线程，清理代码别默认还在主线程。**

### 坑 3：后台线程读了 Unity API

`HeartBeatState.Reset`（收包/连接回调线程调用）里读 `Time.realtimeSinceStartup` → `UnityException: can only be called from the main thread`。**修复：Reset 不读 Time，时钟基点由主线程 `UpdateByRealTime` 每帧维持（收包清账后下一帧差值即以当前时刻起算，语义不变）。教训：工具方法被多线程调用时， Unity API（Time/Object 等）一个都不能碰。**

### 坑 4：失败出口的"二次关闭"

重连失败：`catch` 里 `CloseAll()`（转圈框已被关并移出 UIGroup）→ `finally` 又 `Close(转圈框)` → `UIGroup.Remove` 抛"无法找到界面 id"。**教训：多个出口都做了同一件收尾时，不要再补一个"兜底"收尾——二次执行就是异常源。而且这个坑在第 1~4 次重试时潜伏（转圈框还开着），恰好第 5 次耗尽才炸。**

### 坑 5：快门与画画错位（Blur 黑帧）

模糊背景截屏：`enabled=true`（开快门）→ `await Yield(LastPostLateUpdate)`（等渲染）→ `enabled=false`（关快门）。但该等待的恢复点在**当帧渲染之后**——重构前窗口从按钮同步回调打开（快门开在渲染前，当帧拍到）；重构后全走异步链（快门开在渲染后，关快门前再无渲染点）→ 冻结帧恒黑。**修复：`await UniTask.NextFrame()` 让快门必然覆盖下一次渲染。教训：跨帧等待的"恢复点在帧内哪个位置"决定了代码观察到的世界——同一个"等一帧"，等的位置不同，看到的世界完全不同。**

## 五、自测（随学随考）

### 题目

1. 断线重连的触发条件有哪四道闸？顺序为什么敏感？
2. 玩家点"退出登录"，为什么不会触发自动重连？
3. 被顶号时客户端靠什么知道"我是被顶的"而不是"网断了"？
4. 停服务器 10 秒再启动，客户端经历了什么？（按退避序列说）
5. 为什么"原地复活"不需要服务器做快照回灌？
6. `PlayerInfo == null` 的判空为什么失效？正确判据是什么？
7. `HeartBeatState.Reset` 为什么不能读 `Time.realtimeSinceStartup`？
8. 重连失败 5 次后玩家有哪些出路？

### 答案

1. 非 Lost 忽略 → 未进游戏（Id ≤ 0）忽略 → 被顶标记 → 重入防护。顺序敏感：被顶必须在重入之前查（否则重连中被顶会被重入防护吞掉），未进游戏必须在最前（登录期一切断线都忽略）。
2. 登出走 `Close(Active)`（主动关闭），重连编排第一道闸就把非 Lost 全部忽略。
3. 靠服务器踢人前先推的 `NotifyPrompt(Type=5)` 消息——客户端置"被顶标记"，随后的 `Closed(Lost)` 读标记走弹提示回登录分支。断线原因（CloseReason）区分不了被顶和普通断线（都是 Lost）。
4. 断线（Lost）→ 弹转圈框 → 第 1 次退避 2s 后拨号失败（主动拒绝）→ 退避 3s 再试失败 → …… 服务器重启后的下一次退避拨通 → 静默重登 → 回主界面。
5. 服务器断线只删会话不删实体：Actor + 内存 State 有约 15 分钟宽限，重连走全新登录认领同一份活数据；超时被回收也从 Mongo 重读落库数据。
6. `PlayerManager` 构造就 `new PlayerInfo()`，对象永非 null。正确判据 `PlayerInfo.Id > 0`（登录成功才有 Id）。
7. 它在后台收包/连接回调线程被调用，而 `Time.realtimeSinceStartup` 仅主线程可访问。基点改由主线程 `UpdateByRealTime` 每帧维持，Reset 只清流逝/丢失计数。
8. 「重连失败」框两选：【再试一次】（重新 `StartReconnectFlow`，退避计数重置）/【返回登录】（`LogoutFlowAsync` 回登录界面）。

## 结语

断线重连的本质：**频道把"死亡原因"讲清楚（CloseReason），框架把"难做对的原语"沉淀下来（三件套），Game 层把"策略"编排起来（分流/退避/重登）**。而本篇踩坑实录的五连坑提醒我们：网络代码的敌人从来不是"写不出",而是"跑起来才知道"——判空、线程、帧时序、二次执行，每一个都编译通过、每一个运行时才炸。复核它们最好的办法只有一个：**真的断一次网。**
