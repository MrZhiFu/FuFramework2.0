# 10 · 服务器主动推送（Notify 是 TCP 的独有话语权）

> 本篇范围：TCP 里服务器怎么主动推送消息——从服务器 `WriteAsync` 发出一条 `INotifyMessage`，到客户端三级分流、按绑定表派发到 `[NotifyMessageHandler]`；以及派发阀门缓冲队列"为什么不回放错"的四道保险。
> 前置：06 篇（RPC 请求-响应）、09 篇（HTTP 与 TCP 的分工）。

---

## 一、What：推送是什么，和 RPC 差在哪

一句话认知：

> **推送 = 服务器想说话时，直接对着它握着的那条 TCP 线开口；客户端不需要先问，只要"接住"并按事先约好的处理方法响应。**

两条记忆锚点：

- **RPC**：`await` 挂起等待回复，动手的是客户端——"我问→你答"，靠 `UniqueId` 配对（06 篇）。
- **Notify（推送）**：没有请求端、没有 await、没有回应者——**服务器主动、客户端被动接收**。协议里它对应 `INotifyMessage` 接口，服务器 `MessageProtoHelper` 会把这类类型登记进消息映射（`Abstractions/MessageProtoHelper.cs:169`）。

---

## 二、Why：为什么只有 TCP 能推送；为什么必须有阀门

### 2.1 推送是 TCP 独占的能力

HTTP 是"你寄信它回信"——服务器永远没机会在你没寄信时开口。TCP 长连接是**持续挂着的双向线路**，服务器手里始终握着这条 `netWorkChannel`，随时能写。所以"主动推送"这件事，本质是**连接形态决定的**：只有持续双向的 TCP 做得到。

### 2.2 地图：「增量更新」vs「全量基线」

推送基本都是**增量**（"背包多了 1 金币"、"旁边刷新了一个 Boss"）。而增量**必须先有基线**才有意义（"你背包现在有：苹果×3、金币×100"）。登录时存在一个危险窗口：**TCP 连接已建立，但你还没拉完全量基线**。这时推送若直接派发，会覆写还没建好的 UI 数据。

这就是派发阀门存在的理由——挂起（推进入缓冲）→ 基线就绪 → 恢复（按序回放）。

## 三、How：完整链路（发 → 走 → 接）

### 3.1 服务器怎么"主动开口"

**Step 1｜声明"我是推送"** —— 业务消息类实现 `INotifyMessage` 空接口：

```csharp
// Server: FuFramework.Proto/Proto/Bag.cs
public sealed class NotifyBagInfoChanged : MessageObject, INotifyMessage   // ← 我是推送
```

**Step 2｜业务变动时构造并发给玩家** —— 服务器持有玩家的 `INetWorkChannel`，调用它的 `WriteAsync`（`Abstractions/INetWorkChannel.cs:33`）就是"开口"：

```csharp
// Server: Hotfix/Logic/Player/Bag/BagComponentAgent.cs:51
[Service]
public virtual async Task UpdateChanged(INetWorkChannel netWorkChannel, Dictionary<int, long> itemDic)
{
	var notifyBagInfoChanged = new NotifyBagInfoChanged();          // ① 构造推送
	... // 遍历变了哪些物品，组装 NotifyBagItem
	await netWorkChannel.WriteAsync(notifyBagInfoChanged);          // ② 写进TCP通道，主动开口！
}
```

> 像挂着电话：对面有了新情况（背包变化）直接开口说，你不需要先喊"我问问"。

### 3.2 线路上怎么走：同一条管道、同一套信封

推送**不新开通道**，和 RPC 共用同一条 TCP 连接、同一个"包头+包体"信封（03 篇），区别仅在于包头 `OperationType` 标记为"通知"。对服务器来说发推送和发响应是同一件事——**差别在客户端怎么"认领"**。

### 3.3 客户端怎么"接住"：三级分流 → 派发

收包排水核心 `Channel/NetworkChannelBase.Receive.cs:45-102` 的 `ProcessReceived`，每条消息过三道闸门：

```
收到一条消息 msgObj
  ├─ ① IHeartBeatMessage？  → 心跳保活侧信道，跳过业务派发
  │       （例外：双实现 INotifyMessage 的 NotifyHeartBeat 网开一面走派发）
  ├─ ② m_rpcState.TryReply(msgObj) 命中？ → 这是某条 RPC 响应的回包，配回 await（06 篇）
  └─ ③ 都没中 → DispatchNotify(msgObj)      ← 到这里的就是"服务器主动推送"！
                    └─ NotifyMessageHandlerRegistry.TryDispatch(msgObj)
                         查绑定表：消息类型 → 该类型所有 handler（按优先级排好序）
                                   ↓
              [NotifyMessageHandler] 标注的方法被调起，例如"刷新背包UI"
```

**业务侧只需一步**——在方法上标 `[NotifyMessageHandler]`，声明即生效（`NotifyMessageHandlerRegistry.cs:15-16`，无手动注册）：

```csharp
[NotifyMessageHandler]
public void OnNotifyBagInfoChanged(MessageObject msg)   // 处理背包变化推送
{
	var notify = (NotifyBagInfoChanged)msg;
	// 更新背包界面...
}
```

中间"绑定表"零反射生成（铁律 4）：生成脚本编译期扫出 `[NotifyMessageHandler]` 方法 → 产出 `MessageRegistry.gen.cs` 的 `RegisterNotifyHandlers` → 启动 `BindNotify` 一次性写表，运行期只是"查表 + 调委托"。

### 3.4 派发阀门：挂起 / 恢复 / 清空

```csharp
SuspendNotifyDispatch()   // 连接后、拉基线前：推送进缓冲队列（保到达顺序）
...拉取全量基线...
ResumeNotifyDispatch()    // 基线就绪：按序回放缓冲 → WinMain
```

用法见 `NetworkModule.API.cs:189/195`（门面转发）与 `Network/README.md:79-80`（登录流程），实现全在 `NotifyMessageHandlerRegistry.cs`。

## 四、阀门缓冲为什么"不回放错"（四道保险）

"排队 \( `Queue` FIFO \)" 只是最浅的保序；"不回放错"实际覆盖四种错，代码每种都堵了（全在 `NotifyMessageHandlerRegistry.cs`，源文照录）：

### ① 顺序错乱 → FIFO 队列

```csharp
// TryDispatch 挂起分支：进队尾
if (s_dispatchSuspended) { if 满则丢最旧; sr_bufferedNotifyQueue.Enqueue(msgObj); return true; }
// ResumeDispatch 回放：出队头
while (sr_bufferedNotifyQueue.Count > 0 && !s_dispatchSuspended)
	DispatchInternal(sr_bufferedNotifyQueue.Dequeue());
```

所有 `Enqueue` 只发生在 `TryDispatch` 这一个入口，老消息永不排到新消息后。

### ② 并发写错 → 队列只有"主线程"一个写手

收包线程（线程池）只做 `m_waitingHandleMsgLkList.AddLast`（带锁，见 `Receive.cs:62-63` 注释）；**出队、判断、进缓冲、回放全部在主线程 `ProcessReceived`/`ResumeDispatch` 串行**。单线程独写 = 无并发、无交错，连锁都不用加。

### ③ 回放到一半被打断 → 循环每步检查挂起标志

```csharp
while (sr_bufferedNotifyQueue.Count > 0 && !s_dispatchSuspended)   // 每轮都看标志
	DispatchInternal(sr_bufferedNotifyQueue.Dequeue());
```

某条 handler 处理中再次 `SuspendDispatch()` → **回放立刻停，剩余留在队列**；新到推送见 `true` 也老实排到队尾。下次 `Resume`：先回放老消息、再回放新消息，先后顺序依旧正确——"半途再挂起"不会让该缓冲的提前放出去，也不会让先到的排到后到的后面。

### ④ 串号 → 登出必 `ClearBuffer`

推送是增量，属于某个账号的基线。切号/登出前不清缓冲，残留的旧账号推送会在新账号回放出来——**串号**。`ClearBuffer()`（`:106-109`）在登出/切号时整队丢弃、不回放。配合**单频道门面模型**（客户端仅一条 TCP 连接），全局只有一队一阀，不存在多频道互串。

### 兜底：满则丢最旧 + 警告

上限 `MAX_BUFFERED_NOTIFY_COUNT = 1024`（`:59`）——业务忘了 `Resume` 也不会无限涨内存，满了丢弃最旧一条并 `LogWarning`（丢一次增量（有日志可查）比卡爆进程安全）。

> 补一个底层设计：消息**先 `Dequeue` 再 `Dispatch`**，单个 handler 抛异常被就地隔离（`DispatchInternal` 的 try-catch），不影响队列剩余消息继续回放——不会"消息还在队列里却被重复处理"。

## 五、自测（随学随考）

### 题目

1. 推送和 RPC 的核心区别是什么？
2. 服务器通过哪个方法把推送写到 TCP 通道？通道接口要求"调用前保证处于什么状态"？
3. 客户端收到一条消息，三级分流按什么顺序？为什么先试 RPC 再走 Notify？
4. 为什么必须有派发阀门？"增量 vs 基线"具体指什么？
5. 缓冲队列用什么数据结构 + 唯一写手是谁，怎么保证安全？
6. 回放过程中某 handler 再次挂起会发生什么？
7. 登出时 `ClearBuffer` 防的"串号"是什么？
8. 缓冲积压超过 1024 条会发生什么？

### 答案

1. RPC 是客户端主动 `await` 等回复、靠 UniqueId 配对；推送没有请求端、没有 await、没有回应者，服务器主动发、客户端被动接。
2. `INetWorkChannel.WriteAsync(INetworkMessage msg, int errorCode = 0)`；要求调用时网络通道处于打开状态（`INetWorkChannel.cs` 注释）。
3. 先心跳截流 → 再 `m_rpcState.TryReply`（RPC 响应配回 await）→ 最后 `DispatchNotify`。先 RPC 是因为"配回 await"的语义强于"按表派发"——挂了 N 条 await 请求，响应必须认领回各自请求，而推送没有配对需求。
4. 推送是增量更新，必须先有全量基线才有意义（"背包多了 1 金币"要靠"现在有 3 金币"才可解释）。登录存在"连接已建立但基线未就绪"窗口，直接派发会覆写未建好的 UI，所以挂起入缓冲、就绪后按序回放。
5. `Queue<MessageObject>`（FIFO）；唯一写手、唯一读者都是主线程（线程池只把原始消息放进**带锁的待处理链表**，出队/判定/进缓冲/回放全在主线程串行）——无并发即无交错。
6. `while` 每轮检查 `s_dispatchSuspended`，立即停止回放，剩余留在队列；之后新到的推送排到队尾。下次恢复先老后新，顺序仍对。
7. 把旧账号的增量消息回放到新账号界面上（A 的背包数据刷到 B 的窗口）。`ClearBuffer` 整队丢弃不回放。
8. 满 1024 丢最旧一条并 `LogWarning`（提示检查是否忘记 `Resume`），内存不会无界增长。

---

## 结语

**服务器主动推送 = 消息声明 `INotifyMessage` → 服务器 `channel.WriteAsync` 写进握着的 TCP 连接 → 客户端收包先试心跳/RPC、没配上就按绑定表派发到 `[NotifyMessageHandler]`。** 它与 RPC 共用同一条线和同一套信封，差别只在"谁先开口"和"客户端认领方式"；而"主动开口"本身，只有持续双向的 TCP 做得到。至于阀门缓冲"不回放错"，一句话：**FIFO 保顺序 + 主线程独写防并发 + 回放中可再挂起防越位 + 登出 Clear 防串号**——顺序靠队列，安全靠"只有一个写手、且每一步都可叫停"。
